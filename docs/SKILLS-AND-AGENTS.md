# SKILLS-AND-AGENTS: что установить агенту и как использовать

Идея: один агент пишет код, **отдельные узкоспециализированные агенты** проверяют его с холодной головой. Ревьюер не должен быть тем же контекстом, что писал код, иначе он повторяет его слепые пятна.

> Пути, имена пакетов и формат конфигурации OpenCode и MCP-серверов меняются между версиями. Всё, что ниже помечено "проверь", сверь с актуальной документацией перед установкой. Версии пакетов фиксируй (не `latest`), особенно для MCP-серверов: они исполняют код на твоей машине.

## 1. Что уже лежит в пакете

### Навыки (`skills/` → `.opencode/skill/`)
| Навык | Когда включается |
|---|---|
| `session-protocol` | начало и конец каждой сессии |
| `db-migrations` | любые изменения схемы |
| `booking-engine` | всё, что связано с бронями (Сессия 11 и далее) |
| `pwa` | service worker, manifest, офлайн, push (Сессии 13, 15) |
| `pwa-design` | вёрстка и поведение PWA-интерфейса: safe areas, баннеры, standalone (Сессии 4, 15, 16) |
| `design-system` | любой UI, работа строго по `docs/DESIGN.md` (Сессии 4, 6–9, 12–16) |
| `a11y` | формы, календарь, галерея, модалки; проверки axe |
| `security-checklist` | API, авторизация, файлы, деплой, платёжная часть |
| `testing` | написание тестов любого уровня |

### Агенты-проверяющие (`agents/` → `.opencode/agent/`)
| Агент | Роль | Права |
|---|---|---|
| `@code-reviewer` | корректность, читаемость, соответствие ТЗ и CONSTITUTION, качество тестов | только чтение, может запускать команды |
| `@security-reviewer` | уязвимости, IDOR, секреты, файлы, заголовки | только чтение |
| `@db-reviewer` | миграции, индексы, EXPLAIN, транзакции | только чтение, только dev-база |
| `@ui-reviewer` | экран против DESIGN.md, адаптивность, состояния, доступность, PWA-детали | только чтение, браузер и Lighthouse |
| `@qa-tester` | тест-план, автотесты (Vitest, Playwright), поиск багов | пишет **только тесты**, код приложения не меняет |

Формат файлов агентов (frontmatter `description`, `mode: subagent`, `tools`) соответствует схеме OpenCode на момент написания. Проверь актуальную схему в документации OpenCode (раздел про agents): в новых версиях права могут задаваться через `permission`, а не `tools`.

## 2. Что доустановить

### 2.1 Готовые навыки из внешних источников
- **frontend-design** (из публичного репозитория навыков Anthropic, `anthropics/skills`). Даёт общие принципы "не шаблонного" интерфейса: осмысленная типографика, композиция, осторожность с банальными паттернами. Он дополняет `design-system`, но **не заменяет** его: наш `DESIGN.md` приоритетнее. Проверь: какой путь и формат подхватывает твой OpenCode (`.opencode/skill/` или совместимая папка `.claude/skills/`), и прочитай `SKILL.md` перед включением (навыки это инструкции, которые исполняет агент; не ставь непроверенные).
- Навыки из чужих сборок "на все случаи" не ставь без чтения: лишние инструкции раздувают контекст и конфликтуют с твоими правилами.

### 2.2 MCP-серверы (инструменты, которые агент вызывает сам)
| Инструмент | Зачем | Когда нужен |
|---|---|---|
| **Playwright MCP** (`@playwright/mcp`) | агент открывает приложение в реальном браузере, делает скриншоты на 360/768/1280, кликает по сценариям | Сессии 4–16, критично для `@ui-reviewer` и `@qa-tester` |
| **Chrome DevTools MCP** (`chrome-devtools-mcp`) | Lighthouse, трассировка производительности, консоль, сеть, эмуляция устройств и офлайна | Сессии 8, 10, 15, 16 |
| **Context7** (`@upstash/context7-mcp`) | актуальная документация библиотек (Fastify, Kysely, Workbox, react-day-picker, vite-plugin-pwa), меньше выдуманных API | все сессии с новыми библиотеками |
| **Postgres MCP (read-only)** | агент смотрит схему и гоняет `EXPLAIN` на dev-базе | Сессии 2, 10, 11; **только dev, только чтение, никогда прод** |

Пример подключения в `opencode.json` (проверь актуальную схему в документации OpenCode):

```json
{
  "mcp": {
    "playwright": {
      "type": "local",
      "command": ["npx", "-y", "@playwright/mcp@<закреплённая-версия>"],
      "enabled": true
    },
    "context7": {
      "type": "local",
      "command": ["npx", "-y", "@upstash/context7-mcp@<закреплённая-версия>"],
      "enabled": true
    }
  }
}
```

Не включай все серверы всегда: у каждого свои описания инструментов в контексте. Playwright и Context7 держи включёнными постоянно, DevTools и Postgres только в сессиях, где они нужны.

### 2.3 Обычные инструменты проекта (не навыки, а зависимости и CLI)
| Инструмент | Для чего |
|---|---|
| `eslint-plugin-jsx-a11y`, `@axe-core/playwright` | автоматические проверки доступности (линт и e2e) |
| `lighthouse` или `@lhci/cli` | отчёты Lighthouse в CI, порог по Performance/A11y/BP/SEO |
| `gitleaks` | поиск секретов в коде и истории (локально и в CI) |
| `pnpm audit` (или аналог) | известные уязвимости зависимостей в CI |
| `vitest --coverage` | покрытие как сигнал, не как цель |
| `autocannon` или `k6` | нагрузочные замеры каталога и брони (Сессии 10, 11) |
| `knip` | поиск неиспользуемых файлов, экспортов и зависимостей |
| `husky` + `lint-staged` | быстрые проверки перед коммитом |
| `playwright` (CLI) | e2e и скриншоты |

## 3. Кто ревьюит какую сессию

## 4. Как запускать ревью

В конце сессии основной агент (или ты руками) пишет:

```
@code-reviewer проверь изменения текущей ветки по docs/SESSIONS.md, Сессия N.
@security-reviewer проверь изменения текущей ветки.
```

Ты можешь запускать ревьюверов и **в новом чате отдельно**: так контекст чистый и оценка независимее. Для критичных сессий (3, 11, 17) рекомендуется именно так, а при возможности другой моделью, чем писавшая код: разные модели ловят разные ошибки.

## 5. Практические предупреждения
- Ревьюеры тоже ошибаются и придумывают замечания. Решение о правке принимаешь ты. Ложные срабатывания записывай в `LEARNS.md`, чтобы не гонять их повторно.
- Не давай агентам доступ к продовой БД и боевым ключам. Dev и prod разделены окружениями и `.env`.
- Не оставляй MCP-серверы "на автомате" без закреплённых версий и без чтения того, что они делают.
- Ревью увеличивает время сессии примерно на 30 минут (см. `ESTIMATE.md`), но экономит часы переделок в Сессиях 11–17.
