# Конкурентность бронирования: отчёт

Дата: 2026-10-20. База: PostgreSQL 16 в Docker (`staynest-dev-postgres-1`),
API на Node 24 (`tsx`), Windows 11, отдельная тестовая база `staynest_test`.

## Что проверяется

Тест `apps/api/tests/booking-concurrency.test.ts`:

1. Создаёт объявление, открытое для бронирования.
2. Запускает **50 одновременных** `POST /api/v1/bookings` на одни и те же даты
   от 50 разных гостей (у каждого свой аккаунт и свой `Idempotency-Key`).
3. Проверяет, что ровно **1** запрос вернул `201`, а **49** — `409` с кодом
   `booking_dates_unavailable`.
4. Повторяет сценарий **20 раз подряд**: перед каждой итерацией таблицы
   очищаются и создаются заново, даты те же. Так проверяется стабильность
   инварианта, а не разные даты.

Запуск:

```bash
pnpm --filter @staynest/api test booking-concurrency
```

Тест входит в обычный `pnpm test`; последний прогон — 2026-10-20, все 20
итераций зелёные (весь API-набор: 35 файлов, 379 тестов, ~2–3 минуты в
зависимости от машины).

## Почему это корректно

Защита трёхуровневая, и тест проверяет именно результат, а не реализацию:

| Уровень | Механизм | Что даёт |
|---|---|---|
| 1 | `SELECT users ... FOR UPDATE` | Сериализует заявки одного гостя и делает точным лимит 5 активных `pending` |
| 2 | `SELECT listings ... FOR UPDATE` | Второй запрос ждёт коммита первого; после ожидания quote видит занятость |
| 3 | `EXCLUDE USING gist (listing_id WITH =, stay_range WITH &&) WHERE status IN ('pending','confirmed')` | Последняя линия: даже прямой SQL и обход приложения не создадут пересечение |

Ошибка exclusion constraint в PostgreSQL — `SQLSTATE 23P01`; сервис ловит её и
превращает в `409 booking_dates_unavailable` (не `500` и не `23505`).

## Что было бы без блокировки объявления

Проверка занятости «прочитать → решить → вставить» сама по себе не атомарна:
два запроса читают пустой диапазон и оба пытаются вставить. Constraint поймает
второго, но пользователь получит честную ошибку только благодаря ему. Блокировка
объявления добавлена, чтобы:

- посчитать цену на момент вставки без гонки с правкой тарифов;
- вернуть `409` до вставки в большинстве случаев (дешевле, чем ловить
  исключение);
- автоматически протухшие `pending` (`expires_at <= now()`) перевести в
  `expired` внутри той же транзакции, чтобы они не занимали даты.

## Что тест не покрывает

- Несколько инстансов API: блокировки БД работают и между процессами, но тест
  запускает один процесс. Отдельный тест на два инстанса не делался (в проде
  один API-контейнер).
- Сетевые таймауты и повторные отправки: идемпотентность проверяется отдельно
  (`tests/bookings-create.test.ts`), здесь каждый гость отправляет один запрос.
- Rate limit: 50 запросов от разных пользователей не должны упираться в лимит
  одного пользователя; это осознанно.

## Вывод

Гарантия «одна успешная заявка на даты» держится на схеме БД, а не на
аккуратности кода. Тест воспроизводит худший сценарий (50 одновременных
запросов, 20 повторов) и стабильно подтверждает инвариант. Подробности
движка — `docs/booking-engine.md`.
