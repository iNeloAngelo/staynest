## Что означают цифры

- **`packages/shared`** — zod-схемы и чистые функции. 87 % — это те места, где
  ошибка ломает контракт API и web одновременно (валидация дат, денег, полей
  брони), поэтому они покрыты почти полностью.
- **`apps/web`** — компоненты и хуки на Testing Library + jsdom. 73,7 % —
  покрыты формы, календарь, карточки, состояния, i18n-ключи; не покрыты
  декоративные части (иконки, анимации, некоторые layout-компоненты) и
  страницы, которые проверяются e2e.
- **`apps/api` (юнит)** — 39,8 % от **всех** файлов `src`. Так выглядит потому,
  что в знаменатель входят маршруты, репозитории и SQL-слой, которые
  проверяются интеграционными тестами на настоящем Postgres, а не юнит-тестами.
  Для бизнес-ядра цифры другие:

## Почему API-покрытие считается отдельно

Полный прогон API с инструментацией v8 на интеграционных тестах идёт
неприемлемо долго: 50×20 конкурентных заявок и SSE-тесты с реальными таймерами
под инструментацией растягиваются с 170 с до десятков минут. Поэтому:

- `pnpm test` (в CI) гоняет **все** тесты без покрытия — это источник истины;
- покрытие снимается отдельно: юнит-тесты API, весь web, shared;
- в отчёте не делается вид, что 39,8 % — это «покрытие API».

Команды:

```bash
pnpm --filter @staynest/shared exec vitest run --coverage
pnpm --filter @staynest/web exec vitest run --coverage
pnpm --filter @staynest/api exec vitest run src --coverage
```

## Ограничения

- Покрытие не является порогом в CI (ADR-098): оно показывает, где тестов нет,
  но не заменяет проверку поведения.
- Интеграционные тесты API не измеряются — их ценность в проверке SQL,
  транзакций и ограничений БД, а не в процентах.
- E2E не измеряется: два сценария проходят весь путь в браузере и проверяют
  то, что юнит-тесты не видят (SSE, офлайн, очистка кэшей).
- `booking-concurrency.test.ts` исключается из покрытия осознанно (см. выше);
  в обычном прогоне он обязателен.
