# SECURITY: модель угроз и защита StayNest

Безопасность работает слоями: если один слой не сработал, его страхует следующий. Абсолютной защиты не существует. Цель: сделать взлом дорогим и неинтересным, не потерять данные при ошибке и быстро заметить проблему. Ориентиры: OWASP Top 10, OWASP API Security Top 10, OWASP ASVS (уровень 1 как минимум).

Этот документ читают перед Сессиями 3, 5, 6, 11, 13, 15, 17, 18, 19 и 20 и при любом изменении авторизации, файлов, платежей и деплоя.

## 1. Что защищаем и от кого

**Что защищаем:** аккаунты и сессии; персональные данные (email, телефон, адрес объекта до подтверждения брони); целостность бронирования (никаких двойных броней и подмены цены); доступность сервиса; сервер и данные на нём; (в будущем) деньги.

**От кого:**
| Нарушитель | Что делает |
|---|---|
| Анонимные боты | массовая регистрация, спам, перебор паролей, сканирование уязвимостей |
| Злонамеренный пользователь | лезет в чужие объявления и брони, подменяет данные, грузит вредоносные файлы |
| Злонамеренный хозяин или гость | спамит заявками, блокирует чужие даты, мошенничает с ценами |
| Владелец утёкшего пароля | атака повторным использованием чужих паролей (credential stuffing) |
| Цепочка поставок | вредоносная или уязвимая зависимость, MCP-сервер, скомпрометированный пакет |
| Ошибка разработчика или агента | секрет в git, открытый порт, забытая проверка прав |

## 2. Регистрация и аккаунты

| Мера | Как делаем |
|---|---|
| Пароли | argon2id (параметры по рекомендациям OWASP, не ниже 19 МиБ памяти и 2 итераций; настраиваются через env). Минимум 10 символов, максимум 128, без принудительных "спецсимволов" (они снижают качество паролей), но с проверкой по списку распространённых и утёкших паролей (локальный список топ-10 000 или сервис k-anonymity). Пароль не логируется и не возвращается никогда |
| Подтверждение email | при регистрации создаётся одноразовый токен (в БД только его хэш, срок 24 часа, одноразовый), письмо со ссылкой. **Без подтверждённого email нельзя** входить (при включённом флаге), публиковать объявления и отправлять заявки (флаг `REQUIRE_EMAIL_VERIFICATION`: для демо можно отключить, на проде включён и `false` запрещён). Подтверждение задаёт пароль заново, чтобы чужой регистрацией нельзя было активировать аккаунт с паролем атакующего |
| Сброс пароля | одноразовый токен с коротким сроком (1 час), хэш в БД, после смены пароля отзываются все сессии. Ответ на запрос сброса всегда одинаков ("если такой email есть, мы отправили письмо") |
| Защита от перебора | rate limit по IP и отдельно по email (логин, регистрация, сброс), прогрессивная задержка вместо жёсткой блокировки (жёсткая блокировка позволяет злоумышленнику "заблокировать" чужой аккаунт). Единые сообщения об ошибках входа |
| Защита от перечисления пользователей | ответы регистрации, входа и сброса не раскрывают, существует ли email |
| Боты | honeypot-поле и лимиты; для публичного прода опционально капча-вызов (например, Cloudflare Turnstile) только при подозрительной активности |
| Сессии | короткий access (15 мин) и refresh (30 дней) в httpOnly cookie с ротацией и обнаружением повторного использования (при повторе старого токена отзывается вся цепочка). Список активных сессий и "выйти на всех устройствах" |
| Смена критичных данных | смена пароля и email требует текущего пароля, после смены сессии отзываются |
| Одноразовые токены | везде хэш в БД (SHA-256), сравнение за постоянное время, срок жизни, пометка использованного |
| Телефон и адрес | не показываются публично, адрес раскрывается гостю только после подтверждения брони |
| Закрытие аккаунта | мягкое удаление, анонимизация персональных данных по запросу |

## 3. Как могут взломать и как защищаемся

| Атака | Как это выглядит у нас | Защита | Проверка |
|---|---|---|---|
| **SQL-инъекция** | в поле поиска `q`, фильтрах, сортировке подставляют SQL | только параметризованные запросы (Kysely); запрет сырого SQL с пользовательским вводом (линт-правило на `sql.raw`); сортировка только по whitelist значений | тесты с payload-ами (`' OR 1=1 --`, `;DROP`), ZAP-скан |
| **XSS** (внедрение скрипта) | в названии дома, описании, сообщении гостя | React экранирует вывод, `dangerouslySetInnerHTML` запрещён линтом; пользовательский текст только как текст (без HTML и markdown); CSP; токены в httpOnly cookie недоступны скрипту; SVG-загрузки запрещены | тест на отрисовку `<script>` как текста, проверка CSP |
| **CSRF** (чужой сайт шлёт запрос от имени пользователя) | форма на чужой странице дёргает `POST /bookings` | cookie `SameSite=Lax`, проверка заголовков `Origin` и `Sec-Fetch-Site` на небезопасных методах, только JSON с проверкой `Content-Type`, никаких изменений через GET | тест: запрос с чужим Origin отклонён |
| **IDOR / BOLA** (чужие объекты по id) | `GET /bookings/<чужой id>`, `PATCH /listings/<чужой id>`; самая частая реальная уязвимость API | проверка владения в **каждом** эндпоинте на уровне сервиса; для чужого ресурса ответ 404; UUID вместо последовательных id (не защита, но усложняет угадывание) | общий параметризованный тест-матрица `tests/security/idor.test.ts`: для каждого защищённого эндпоинта пользователь B пытается обратиться к ресурсу пользователя A. Расширяется в каждой сессии |
| **Массовое присваивание** | клиент шлёт `owner_id`, `status`, `total_minor`, `role` в теле | zod-схемы в строгом режиме с явным списком разрешённых полей; `owner_id`, `guest_id`, `status`, цены берутся только с сервера | тест: лишние поля отбрасываются или дают 422 |
| **Подмена цены** | клиент присылает свою сумму | сумму считает только сервер, клиентская только для показа | тест: любое `total` в запросе игнорируется |
| **Гонки и двойная бронь** | два параллельных запроса на одни даты | exclusion constraint в БД, блокировка строки объявления, идемпотентность | тест на 50 параллельных заявок |
| **Брутфорс и credential stuffing** | перебор паролей, пароли из утечек | rate limit, argon2id, проверка по утёкшим паролям, логирование и оповещение об аномалиях | тесты лимитов |
| **Загрузка вредоносных файлов** | `.php` под видом `.jpg`, полиглоты, "бомба" из огромного изображения, путь `../../`, SVG со скриптом | тип по содержимому (magic bytes), только JPEG/PNG/WebP/HEIC, лимит размера и **`limitInputPixels`** в sharp (защита от decompression bomb), полная перекодировка (всё постороннее вырезается, EXIF удалён), имена файлов генерирует сервер (UUID), `X-Content-Type-Options: nosniff`, хранилище без исполнения, опционально ClamAV | тесты с подделанными файлами и гигантскими пикселями |
| **DoS и злоупотребление ресурсами** | тяжёлые запросы поиска, огромные тела, массовые заявки | лимиты размера тела, потолок `limit` пагинации, максимум диапазона дат (например 365 дней) и числа значений в фильтрах, `statement_timeout` в Postgres, таймауты запросов, rate limit, лимит активных `pending` у гостя (например, не больше 5) | нагрузочный тест |
| **Раскрытие информации** | трассировки в ошибках, лишние поля в ответах, публичный `/metrics` | единый формат ошибок без внутренних деталей, явные DTO для ответов (не отдаём строки БД целиком), `/metrics` и консоль MinIO не публикуются, `X-Powered-By` убран | ручной просмотр ответов, ZAP |
| **Clickjacking** | сайт открывает наш в невидимом iframe | `Content-Security-Policy: frame-ancestors 'self' https://web.telegram.org https://*.telegram.org` (Mini App), для остальных родителей фрейм запрещён | проверка заголовков |
| **Open redirect** | `/login?next=https://evil.com` | `next` только относительные пути нашего приложения | тест |
| **SSRF** | сервер ходит по URL, заданному пользователем | в MVP серверных запросов по пользовательским URL нет; если появятся, только whitelist | ревью кода |
| **Утечка секретов** | ключ в git, в образе Docker, в логе | `.env` вне git, `gitleaks` в pre-commit и CI, секреты в рантайме, не в образе, права на `.env` 600, ротация при подозрении | CI |
| **Цепочка поставок** | уязвимый или подменённый npm-пакет | lockfile, закреплённые версии, `pnpm audit` и обновления через PR (Renovate или Dependabot) с ревью, минимум зависимостей (новая только с записью в `DECISIONS.md`), проверка скриптов установки (по возможности запрещены lifecycle-скрипты, проверь настройку своей версии pnpm), MCP-серверы только с закреплёнными версиями | CI |
| **Атаки на сервер (VPS)** | перебор SSH, открытые порты, устаревшее ПО | вход только по ключам, пароль отключён, не под root, фаервол (только 80/443 и SSH), `fail2ban`, автообновления безопасности, Postgres и консоль MinIO не опубликованы наружу, контейнеры от непривилегированного пользователя с лимитами ресурсов, разные docker-сети | чек-лист Сессии 17 |
| **Перехват трафика** | чтение данных в сети | только HTTPS (Caddy, автосертификаты), HSTS, cookie с `Secure` | SSL Labs / проверка заголовков |
| **Злоупотребление Web Push** | подписать чужой endpoint, слать спам | подписка привязана к пользователю, валидация формата endpoint (https), удаление мёртвых подписок, ограничение частоты отправки | тесты |
| **Утечка данных через PWA-кэш** | на общем устройстве после выхода следующий человек видит брони из кэша | **при выходе очищаются кэши service worker и IndexedDB**; ответы с персональными данными не кэшируются общими стратегиями; `Cache-Control: private, no-store` для `/me/*` | e2e: login → logout → офлайн → данных нет |
| **SSE** | чужой поток событий | поток только аутентифицированного пользователя, события только его, лимит соединений на пользователя | тест |
| **Поддельный `initData` (Telegram)** | подделка входа через Mini App | проверка HMAC по токену бота, проверка свежести `auth_date`, запрет дубликатов полей, rate limit по IP | тесты (Сессия 19) |
| **Webhook платежей** | подделка "оплачено" | проверка подписи, защита от повтора (идемпотентность по `external_id`), сумма сверяется с БД, статус меняется только по подтверждённому событию | тесты (Сессия 18) |

## 4. Заголовки безопасности (на уровне Caddy и API)
`Content-Security-Policy` (по умолчанию `default-src 'self'`, скрипты только свои, `img-src 'self' data: blob:`, `frame-ancestors 'self' https://web.telegram.org https://*.telegram.org` для Mini App, `object-src 'none'`, `base-uri 'self'`); `Strict-Transport-Security`; `X-Content-Type-Options: nosniff`; `Referrer-Policy: strict-origin-when-cross-origin`; `Permissions-Policy` (отключаем камеру, микрофон, геолокацию, если не нужны); `Cross-Origin-Opener-Policy: same-origin`. Шрифты свои (self-hosted), поэтому внешние источники в CSP не нужны. Это же упрощает PWA офлайн. `X-Frame-Options` не используется: он не умеет allowlist и конфликтует с `frame-ancestors`.

## 5. Данные, логи, приватность
- Минимум данных: храним только то, что нужно для работы.
- В логах нет паролей, токенов, содержимого cookie, телефонов и полных email (маскируем). Есть `request-id` для разбора инцидентов.
- Журнал безопасных событий: неудачные входы, смена пароля и email, сброс пароля, отзыв сессий, подозрительные 403/404 серии. Простое оповещение (например, в Telegram-бот) при всплеске ошибок входа.
- Бэкапы шифруются и хранятся вне сервера. Восстановление проверено.
- **Если в демо будут регистрироваться реальные люди,** их персональные данные подпадают под законодательство (для граждан РФ это 152-ФЗ: согласие на обработку, политика, требования к месту хранения). Самый простой путь для портфолио: демо-аккаунты и пометка "демо, не вводите настоящие данные", а реальную регистрацию включать только после юридической проверки. Это не юридическая консультация, вопрос стоит уточнить у юриста.

## 8. Что делать при инциденте (минимум)
1. Отозвать все сессии: `UPDATE refresh_tokens SET revoked_at = now() WHERE revoked_at IS NULL;`
2. Сменить секреты (JWT-ключи, VAPID, ключи MinIO, пароль БД, токен бота), перезапустить сервисы.
3. Просмотреть логи по `request-id` и журналу безопасных событий, определить, что утекло.
4. Исправить причину, добавить тест, записать в `LEARNS.md`.
5. Если утекли персональные данные реальных пользователей, действовать по требованиям закона об уведомлении.
