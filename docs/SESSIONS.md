# SESSIONS: порядок сборки StayNest

Правила:
- Одна сессия = один отдельный чат OpenCode = один законченный, проверенный отрезок.
- Сессия не начинается, пока предыдущая не прошла Definition of Done (DoD) и не закоммичена в `main`.
- Оценка в часах: **активное время человека** (запуск, ревью, ручная проверка, правки), код пишет агент. Это ориентир, закладывай запас 25%.
- Обязательные: 1–17 и 20. Опциональные: 18 (платёжная заглушка), 19 (Telegram Mini App).

Стартовый промпт для любой сессии лежит в `README.md`.

**Общее правило ревью:** в конце каждой сессии, после зелёных lint, typecheck и тестов, вызываются ревьюверы из `docs/SKILLS-AND-AGENTS.md` (раздел 3). Блокирующие замечания (`blocker`, `major`) исправляются до закрытия сессии. Это входит в DoD каждой сессии и в оценку времени.

**Общее правило UI:** любая сессия с интерфейсом работает по `docs/DESIGN.md` и навыкам `design-system`, `pwa-design`, `a11y`; в DoD добавляется чек-лист дизайн-ревью (DESIGN.md, раздел 8) и скриншоты в `docs/screens/`.

## Сессия 1. Фундамент репозитория
**Цель:** пустой, но рабочий каркас с проверками.
**Задачи:**
- pnpm-монорепо: `apps/api`, `apps/web`, `packages/shared`, общие tsconfig, ESLint, Prettier, editorconfig.
- `infra/docker-compose.dev.yml`: Postgres 16 и MinIO, healthcheck, тома.
- API: Fastify, `GET /api/v1/health` (проверяет БД), pino, загрузка конфигурации из env с валидацией zod, `.env.example`.
- Web: Vite + React + Tailwind, страница-заглушка.
- Vitest в обоих приложениях, один тест на каждое.
- GitHub Actions (или аналог): lint, typecheck, test, build.
- Скрипты корня: `pnpm dev`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- Архитектура по `docs/ARCHITECTURE.md`: каркас `apps/api/src/modules` и `platform`, `apps/web/src/features`, `pages`, `shared`; шаблон модуля и шаблон README модуля; пример готового модуля `health`.
- Автоматические границы: ESLint (`max-lines` 300, `max-lines-per-function` 60, `complexity` 12, запрет глубоких импортов в чужие модули), `dependency-cruiser` (`pnpm depcheck`), `knip`; всё в CI.
- Безопасная база по `docs/SECURITY.md`: helmet, CORS whitelist, лимит тела запроса, `gitleaks` и `pnpm audit` в CI, Mailpit (тестовая почта) в `docker-compose.dev.yml`.
**DoD:** `docker compose up` поднимает инфраструктуру; `pnpm dev` показывает страницу и `/health` отвечает `ok` с `db: up`; CI зелёный; все документы лежат в `docs/`; попытка импортировать внутренности чужого модуля ломает `pnpm lint` или `pnpm depcheck`.
**Оценка:** 3 ч

## Сессия 2. База данных: схема и миграции
**Цель:** вся схема из `DB.md` применяется с нуля.
**Задачи:**
- node-pg-migrate: миграции по группам (расширения и типы; users и токены; справочник; listings и связанные; bookings и аудит; прочее). Каждая с `up` и `down`.
- Сид справочника `amenities`.
- Kysely: типы БД через кодогенерацию, фабрика подключения.
- Интеграционные тесты схемы: exclusion constraint на `bookings` отвергает пересечение, пропускает смежные даты `[10,12)` и `[12,14)`, пропускает пересечение, если одна из броней `declined`; аналогично для `listing_blocks`.
- Скрипт `pnpm db:reset` (drop, migrate, seed).
**DoD:** `pnpm db:reset` отрабатывает на чистой базе; `down` откатывает всё; тесты схемы зелёные; `DB.md` совпадает с миграциями.
**Оценка:** 3 ч

## Сессия 3. Аккаунты и авторизация (API)
**Цель:** безопасная регистрация и вход.
**Задачи:**
- `POST /auth/register|login|refresh|logout`, `GET|PATCH /me`.
- argon2id, access-токен (15 минут) и refresh-токен (30 дней, ротация, `family_id`, отзыв цепочки при повторном использовании) в httpOnly cookie, SameSite=Lax, Secure в проде.
- Rate limit на login и register, проверка Origin для небезопасных методов.
- Формат ошибок problem+json, глобальный обработчик, request-id.
- Тесты: регистрация, дубликат email, неверный пароль, ротация, повторное использование старого refresh, доступ к `/me` без токена.
- Подтверждение email (`auth_tokens`, письма через `platform/mailer`, Mailpit в dev), сброс пароля, смена пароля, список сессий и выход на всех устройствах, флаг `REQUIRE_EMAIL_VERIFICATION`.
- Проверка пароля по списку распространённых и утёкших паролей, единые ответы против перечисления пользователей, rate limit по IP и по email, прогрессивная задержка.
- Модули `auth` и `users` оформлены по ARCHITECTURE.md, события `user.registered`.
**DoD:** все сценарии покрыты тестами; пароль и токены не попадают в логи; ручная проверка через `curl` или REST-клиент описана в отчёте; письма с токенами видны в Mailpit; токены хранятся только в виде хэша.
**Оценка:** 5 ч

## Сессия 6. Фото: конвейер загрузки
**Цель:** надёжная загрузка и хранение изображений.
**Задачи:**
- API: `POST /listings/:id/photos` (multipart), проверка MIME по содержимому, лимит размера, sharp: поворот по EXIF, удаление метаданных (включая GPS), три WebP-варианта (400, 1000, 2000), blurhash, запись в MinIO, запись в `listing_photos`.
- `PATCH .../order`, `PATCH .../cover`, `DELETE` (удаляет файлы из MinIO).
- Caddy/dev-прокси для раздачи `/media` из бакета (публичное чтение только для вариантов фото).
- Web: компонент загрузчика (выбор нескольких файлов, сжатие на клиенте до 2000 px, прогресс, превью, ошибки, drag-and-drop сортировка, выбор обложки, удаление).
- Тесты: отказ на `.exe`, переименованном в `.jpg`, на файл больше лимита; удаление чистит хранилище.
- Защита от decompression bomb (`limitInputPixels`), только растровые форматы, заголовок `nosniff` на раздачу медиа, тесты с поддельными и огромными файлами.
**DoD:** загрузка 5 фото с телефона работает; EXIF GPS не остаётся в файлах; порядок и обложка сохраняются; тесты зелёные.
**Оценка:** 4 ч

## Сессия 11. Движок бронирования
**Цель:** главная технически значимая часть кейса.
**Задачи:**
- `POST /bookings` в транзакции: блокировка строки объявления `FOR UPDATE`, проверка блокировок хозяина, расчёт цены на сервере, `INSERT`, перехват нарушения exclusion (`23P01`) и преобразование в 409 `booking_dates_unavailable`, запись в `booking_events`.
- Идемпотентность по `Idempotency-Key` (повтор с тем же ключом и телом возвращает исходный ответ, с другим телом даёт 422).
- Машина состояний как отдельный модуль с таблицей разрешённых переходов; `confirm`, `decline`, `cancel` с проверкой прав.
- Фоновые задачи pg-boss: истечение `pending` по `expires_at`, завершение подтверждённых после `check_out`, чистка idempotency_keys.
- Тесты: конкурентность (50 параллельных заявок на одни даты: ровно 1 успех, 49 × 409), все допустимые и запрещённые переходы, чужая бронь недоступна, гонка confirm и cancel, истечение.
- Лимиты против спама: не более 5 активных `pending` у гостя, rate limit на создание брони, требование подтверждённого email (при включённом флаге). События `booking.*` через event bus.
**DoD:** тест конкурентности стабильно проходит 20 запусков подряд; запрещённый переход возвращает 409 с кодом; в `docs/booking-engine.md` описана схема и диаграмма статусов.
**Оценка:** 5 ч

## Сессия 17. Деплой на VPS
**Цель:** живая ссылка.
**Задачи:**
- Dockerfile для api и worker (multi-stage), сборка web в статику.
- `infra/docker-compose.prod.yml`: caddy, api, worker, postgres, minio, healthcheck, лимиты ресурсов, сети; Caddy с автоматическим TLS, заголовки безопасности, gzip/zstd, кэш-заголовки для статики.
- Деплой-скрипт (`scripts/deploy.sh`): pull, build, миграции отдельной командой, перезапуск без простоя насколько возможно.
- Бэкапы: ежедневный `pg_dump` с ротацией, копия на внешнее хранилище, **проверенное** восстановление в отдельную базу; бэкап бакета MinIO.
- CI/CD: деплой по тегу или по кнопке.
