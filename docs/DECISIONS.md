# DECISIONS: журнал архитектурных решений

Формат: **ADR-NN. Название.** Статус, контекст, решение, последствия. Агент дописывает новые записи в конец. Статусы: принято, заменено (ссылка на новую), отклонено.

## ADR-001. Монорепо на pnpm workspaces
**Принято.** Общие типы и zod-схемы (`packages/shared`) используются фронтом и бэком, один CI. Последствие: единые версии TypeScript и линтеров.

## ADR-002. PWA как основной канал, Telegram Mini App как опциональная оболочка
**Принято.** У объявлений есть фото, ссылки для шаринга и SEO, это лучше в вебе. Логика авторизации и уведомлений скрывается за абстракцией, чтобы TMA добавлялся без переписывания (Сессия 19).

## ADR-003. Защита от двойного бронирования на уровне БД
**Принято.** `EXCLUDE USING gist (listing_id WITH =, stay_range WITH &&) WHERE (status IN ('pending','confirmed'))`. Приложение лишь преобразует ошибку `23P01` в 409. Последствие: корректность не зависит от количества инстансов API и гонок.

## ADR-004. Заявка `pending` блокирует даты
**Принято.** Иначе хозяин может подтвердить две пересекающиеся заявки. Минус: гость может "занять" даты и не получить ответ. Смягчение: TTL 24 часа и автоматическое истечение.

## ADR-005. Блокировки хозяина в отдельной таблице + блокировка строки объявления
**Принято.** Блокировки (`listing_blocks`) и брони (`bookings`) в разных таблицах, EXCLUDE не работает между таблицами. Поэтому при создании брони транзакция берёт `SELECT ... FOR UPDATE` строки объявления и проверяет блокировки. Альтернатива (одна таблица "занятости") отклонена: разные жизненные циклы и поля.

## ADR-006. Деньги как целые в минимальных единицах
**Принято.** `bigint` + `currency char(3)`. Расчёт только на сервере, снимок разбивки в `bookings.price_breakdown`.

## ADR-007. Модель дат `[)` и тип `date`
**Принято.** День выезда свободен для следующего заезда. Нет таймзон в датах проживания, только в сроках (`timestamptz`).

## ADR-008. Фоновые задачи на pg-boss
**Принято.** Очередь на Postgres, без Redis. Меньше инфраструктуры на одном VPS, транзакционная целостность с данными.

## ADR-009. SQL-first миграции (node-pg-migrate) + Kysely
**Принято.** Ограничения вроде EXCLUDE, partial indexes, generated columns выражаются нативным SQL, ORM их не покрывает. Kysely даёт типобезопасные запросы без скрытой магии.

## ADR-010. Авторизация: httpOnly cookie, короткий access и ротируемый refresh
**Принято.** Токены не доступны JS (защита от XSS-кражи). От CSRF: SameSite=Lax, проверка Origin, отсутствие небезопасных GET. Для Telegram Mini App возможен bearer-режим (Сессия 19).

## ADR-011. Обработка фото на сервере (sharp), хранение в MinIO, раздача через Caddy
**Принято.** Клиент сжимает для экономии трафика, сервер всё равно перекодирует (нельзя доверять клиенту), снимает EXIF, делает три WebP-варианта. В БД только префикс ключа.

## ADR-012. Курсорная пагинация
**Принято.** Стабильна при добавлении данных, не деградирует на больших смещениях. Курсор кодирует кортеж сортировки и `id`.

## ADR-013. Один аккаунт, два режима
**Принято.** Нет столбца `role`. Режим интерфейса хранится на клиенте, права выводятся из владения объектами.

## ADR-014. Поиск: tsvector (russian) + триграммы по городу
**Принято.** Достаточно для MVP без внешнего поискового движка.

## ADR-015. Платежи: только заглушка, данные карт не храним никогда
**Принято.** Реальный провайдер подключается через hosted-страницу или токенизацию; у нас только `external_id` и статус. См. Сессию 18.

## ADR-016. Уведомления: внутренние + SSE + Web Push
**Принято.** Единая точка отправки (сервис уведомлений). Push запрашивается только по действию пользователя.

## ADR-017. Модульный монолит с жёсткими границами
**Принято.** Бэкенд разбит на модули (`modules/*`), фронтенд на фичи (`features/*`); модуль общается с другими только через `index.ts` и события; границы проверяются ESLint и dependency-cruiser. Исключение: read-модели `catalog` и `dashboard` делают SQL-соединения по чужим таблицам только на чтение. Микросервисы отклонены как преждевременная сложность. Детали в `ARCHITECTURE.md`.

## ADR-018. Внутренний event bus для связи модулей
**Принято.** `bookings` публикует события `booking.*`, `notifications` подписан. События публикуются после коммита транзакции; критичные дублируются в очередь pg-boss для повторов. Минус: чуть сложнее отладка, плюс: нет циклических зависимостей.

## ADR-019. Подтверждение email обязательно для публикации и бронирования
**Принято.** Токены одноразовые, в БД хэш, срок жизни ограничен. Флаг `REQUIRE_EMAIL_VERIFICATION` позволяет отключить требование в демо-окружении. Уменьшает массовую регистрацию ботов и спам заявками.

## ADR-020. Защита от перечисления пользователей и перебора без жёсткой блокировки аккаунта
**Принято.** Единые ответы в регистрации, входе и сбросе; rate limit по IP и по email; прогрессивная задержка вместо блокировки (блокировка позволяет злоумышленнику вывести из строя чужой аккаунт).

## ADR-021. S3-хранилище: форк Silo вместо образов MinIO
**Принято.** В сентябре 2026 MinIO удалил образы `minio/minio` из Docker Hub, а `quay.io/minio/minio` перестал отдавать их анонимно (401). Стек требует S3-совместимое хранилище. Используем `pgsty/silo` — поддерживаемый сообществом форк MinIO с тем же S3 API, консолью и `mcli`; образ фиксируется по digest. Приложение работает через стандартный S3-клиент, поэтому замена хранилища не затрагивает код. ADR-011 (обработка фото, WebP, MinIO как хранилище) остаётся в силе: меняется только поставщик образа. Последствие: нужно следить за обновлениями форка; в проде фиксируется конкретный digest.

## ADR-022. Порты локальной разработки: API 3100, Postgres 5433
**Принято.** На машине разработчика порты 3000 и 5432 уже заняты другими проектами. Dev-окружение использует API `3100`, Postgres на хосте `5433` (внутри контейнера остаётся 5432), Vite проксирует `/api` на 3100. В проде порты наружу не публикуются, поэтому на деплой это не влияет.

## ADR-023. Версии инструментов: pnpm 12, TypeScript 5.9, ESLint 9
**Принято.** TypeScript 7 ещё не поддержан `typescript-eslint` (peer `<6.1.0`), ESLint 10 — не поддержан `eslint-plugin-jsx-a11y` 6.10 (peer `<=9`). Фиксируем TypeScript `~5.9.3`, ESLint `~9.39.5`, `@eslint/js` `~9.39.5`. pnpm 12 блокирует lifecycle-скрипты зависимостей: разрешения задаются в `pnpm-workspace.yaml` ключом `allowBuilds` в виде mapping (`esbuild: true`), а не списком. Пересмотреть версии, когда плагины добавят поддержку.

## ADR-024. Tailwind CSS v4 с CSS-first токенами
**Принято.** Используем Tailwind v4 и `@tailwindcss/vite`. Токены дизайн-системы объявляются в `apps/web/src/styles.css` через `@theme` (цвета, шрифты), а не в `tailwind.config.js`. Сессия 4 расширяет набор до полного `docs/DESIGN.md`. Последствие: конфигурация темы живёт в CSS, магические значения по-прежнему запрещены.

## ADR-025. Сборка API через tsup, общий пакет как TS-исходники
**Принято.** `packages/shared` экспортирует `src/index.ts`; API в разработке запускается через `tsx`, а для прода собирается `tsup` с `noExternal: ['@staynest/shared']`. Это убирает порядок сборки пакетов и отдельные `dist` для shared. Минус: пакет нельзя опубликовать как JS-библиотеку без сборки; для монорепо это не требуется.

## ADR-026. Таймаут запросов к БД через переменную окружения
**Принято.** `DB_QUERY_TIMEOUT_MS` (по умолчанию 5000) задаёт `query_timeout` и `statement_timeout` пула pg. Health-check не может висеть бесконечно, а будущие запросы каталога и бронирования ограничены сверху. На перф-данных (Сессия 10) значение поднимается через env без изменения кода. `statement_timeout` дополнительно страхует Postgres от забытых лимитов в ручных запросах.

## ADR-027. Staging-инфраструктура на VPS вместо локального Docker
**Принято.** Postgres для разработки и интеграционных тестов живёт на VPS (`/opt/staynest`, compose `infra/docker-compose.prod.yml`) и публикуется только на `127.0.0.1:5433`. С машины разработчика доступ идёт через SSH-туннель `-L 5433:127.0.0.1:5433`, поэтому `DATABASE_URL` остаётся `localhost:5433` и локальный Docker не нужен. Базы: `staynest` (разработка) и `staynest_test` (тесты). На сервере добавлен swap-файл 2 ГБ: при 1 vCPU и 1.8 ГБ RAM сборка образов иначе падает по памяти. Прод-контур (TLS, Caddy, бэкапы, CI/CD, мониторинг, укрепление) остаётся в Сессии 17. Последствие: разработка зависит от доступности сервера и SSH-туннеля; перед интеграционными тестами нужно проверять соединение.

## ADR-028. Миграции: SQL в ESM-файлах, сид справочника в миграции, типы Kysely генерируются
**Принято.** Миграции — обычные `.js` (ESM) с `pgm.sql` и JSDoc-типами, без ORM-конструкторов: EXCLUDE, generated columns, partial indexes и GIN выражаются нативным SQL. Справочник `amenities` сеется идемпотентной миграцией `0003` (так записано в DB.md, раздел 19), поэтому `db:reset` = drop schema + все миграции. Типы Kysely генерируются `kysely-codegen` в `apps/api/src/platform/db/schema.generated.ts`; файл машинный и исключён из ESLint и Prettier (knip видит его через импорт, лимит строк он не превышает). Кодогенератор запускается с `--date-parser string`, а пул `pg` отдаёт DATE строкой: иначе `date` превращается в `Date` и день сдвигается при сериализации. Последствие: после изменения схемы обязателен `pnpm db:codegen`, иначе типы разойдутся с БД.

## ADR-029. Интеграционные тесты схемы на отдельной базе
**Принято.** Тесты работают только с `DATABASE_URL_TEST` (по умолчанию `staynest_test` на staging-Postgres), перед прогоном пересоздают схему и накатывают миграции, поэтому результат не зависит от предыдущих запусков. Файлы тестов идут последовательно (`fileParallelism: false`), чтобы не конкурировать за одну базу. Без `DATABASE_URL_TEST` блок пропускается: обычный `pnpm test` не требует БД. В CI поднимается сервис `postgres:16`, переменные задаются на уровне job. Последствие: тесты разрушительны и не должны смотреть на dev/prod базу.

## ADR-030. Принятый риск: advisory без патча в dev-зависимости kysely-codegen
**Принято.** `kysely-codegen@0.20.0` через `micromatch` тянет `braces@3.0.3`, для которого есть advisory `GHSA-vfj7-8cjw-p6xm` (stack exhaustion при глубоко вложенных glob-паттернах) без исправленной версии. Кодогенератор запускается только вручную и в CI на доверенных именах таблиц, в рантайм API не попадает. Игнор зафиксирован в `pnpm-workspace.yaml` (`auditConfig.ignoreGhsas`), поэтому одинаково действует локально и в CI; остальные advisory продолжают ломать сборку. Пересмотреть при обновлении `kysely-codegen` или появлении патча.

## ADR-031. Staging-деплой вынесен вперёд Сессии 17
**Принято.** По запросу владельца живой стенд поднимается сразу после Сессии 2, а не в Сессии 17. Состав: Caddy с автоматическим TLS (`infra/Caddyfile`), статика web из multi-stage образа (`infra/Dockerfile.web`), API (`infra/Dockerfile.api`), Postgres, Silo и Mailpit (`infra/docker-compose.prod.yml`). Сборка образов идёт на VPS, миграции — отдельной командой `docker compose run --rm api node dist/migrate.js` (в образ входят `db/migrations` и entrypoint `dist/migrate.js`). В Сессии 17 остаются бэкапы и проверенное восстановление, CI/CD, мониторинг, закрытие root-доступа и финальное укрепление. Последствие: Dockerfile'ы и compose придётся поддерживать на каждой следующей сессии; каждое изменение схемы требует прогона миграций на стенде.

## ADR-032. Access-токен — JWT, refresh — opaque-токен с проверкой активной сессии
**Принято.** Access — короткоживущий JWT HS256 (15 минут) с `sub` и `sid` (family_id) в httpOnly cookie; refresh — случайные 32 байта, в БД только SHA-256. На каждом защищённом запросе guard дополнительно проверяет, что family ещё активна, поэтому logout, смена и сброс пароля действуют немедленно, а не через 15 минут. Плата — один индексный запрос к `refresh_tokens` на запрос. Полностью stateless access отклонён: выход из аккаунта должен отзывать доступ сразу. Ротация refresh, logout, выход на всех устройствах, смена и сброс пароля захватывают `SELECT ... FOR UPDATE` строки `users`, поэтому «выйти на всех» не может проиграть гонку свежему refresh и оставить сессию живой.

## ADR-033. Единые ответы регистрации и сброса против перечисления пользователей
**Принято.** `POST /auth/register` всегда отвечает `202 {status:"accepted", emailVerificationRequired}` и не создаёт сессию, даже если email новый. Существующий email получает письмо «аккаунт уже существует» без токена; новый — письмо подтверждения. `POST /auth/forgot-password` и `POST /auth/resend-verification` всегда `202`, ответ задерживается до минимального времени, чтобы не выдавать существование email. Минус: после регистрации пользователь входит отдельно; плюс: нельзя перебором узнать, зарегистрирован ли email.

## ADR-034. Rate limit и прогрессивная задержка в памяти процесса
**Принято.** Счётчики по IP и email и прогрессивная задержка входа (до 3 секунд после третьей неудачи) хранятся в памяти API. Жёсткий `429` отдаётся только по IP; лимит по email не блокирует верный пароль, а лишь добавляет максимальную задержку к неудачным попыткам, иначе злоумышленник мог бы заблокировать чужой вход пятью запросами. Для регистрации, сброса и переотправки письма лимит по email мягкий: ответ всегда `202`, но письмо сверх лимита не отправляется. Для одного VPS и одного инстанса этого достаточно; счётчики сбрасываются при перезапуске. Жёсткая блокировка аккаунта не применяется: она позволяет вывести чужой аккаунт из строя. При горизонтальном масштабировании счётчики переносятся в Postgres/Redis (Backlog).

## ADR-035. Политика паролей: минимум 10 символов и локальный список утечек
**Принято.** Пароль 10–128 символов, argon2id (19 МиБ, 2 итерации, 1 поток), проверка по локальному списку 10 000 распространённых паролей из SecLists (MIT) и запрет email/имени внутри пароля. Список лежит в сгенерированном TS-файле и попадает в бандл, поэтому проверка не зависит от сети и работает в тестах; сервис k-anonymity не используется. Минимум 10 (а не 8 из ТЗ) взят из `SECURITY.md` как более строгий.

## ADR-036. Зависимости авторизации: @fastify/cookie, jose, @node-rs/argon2, nodemailer
**Принято.** `@fastify/cookie` — разбор и установка httpOnly cookie; `jose` — проверенный JWT HS256 без собственной криптографии; `@node-rs/argon2` — argon2id с готовыми бинарниками (не требует node-gyp и lifecycle-сборки); `nodemailer` — SMTP, в dev/staging Mailpit. Все версии зафиксированы в `pnpm-lock.yaml`. Самописные JWT и SMTP-клиент отклонены как рискованные. Письма отправляются напрямую из `auth` через `platform/mailer`; `user.registered` публикуется для будущего `notifications`.

## ADR-037. Флаг REQUIRE_EMAIL_VERIFICATION блокирует вход, письмо можно переотправить без входа
**Принято.** При `REQUIRE_EMAIL_VERIFICATION=true` вход с верным паролем, но неподтверждённым email возвращает `403 email_not_verified`. Это закрывает pre-registration/squatting: атакующий не получает сессию до подтверждения чужого ящика. Чтобы пользователь не оказался заперт, `POST /auth/resend-verification` принимает `{ email }` без авторизации, всегда отвечает `202` и отправляет письмо только существующему неподтверждённому аккаунту. Подтверждение email принимает `{ token, password }` и заново задаёт пароль: владелец ящика, кликнувший ссылку, выбирает свой пароль, поэтому аккаунт не активируется с паролем того, кто зарегистрировал чужой email (pre-hijack). Успешный сброс пароля по ссылке из письма также подтверждает email. При `REQUIRE_EMAIL_VERIFICATION=false` регистрация сразу ставит `email_verified_at` и письмо не отправляет — это demo/dev-режим, в production флаг `false` запрещён. Проверка подтверждения для публикации объявлений и броней остаётся в Сессиях 5/11, но теперь опирается на реально работающий флаг, а не на мёртвую настройку.

## ADR-038. Зависимости веб-каркаса: формы, i18n, иконки и шрифты
**Принято.** Добавлены `react-hook-form` + `@hookform/resolvers` (валидация по общим zod-схемам из `@staynest/shared`), `i18next` + `react-i18next`, `lucide-react` (иконки из DESIGN.md) и `@fontsource-variable/lora` + `@fontsource-variable/manrope` (self-hosted, без CDN). `zod` добавлен в web напрямую, потому что формы используют его типы и `zodResolver`. Готовая UI-библиотека (MUI, Radix, shadcn) не добавлялась: компоненты дизайн-системы небольшие и должны строго следовать токенам, иначе стили протекают. Последствие: фокус-ловушку, тосты и состояния компонентов тестируем сами; шрифты отдают только совпадающие unicode-подмножества, но в сборку попадают все woff2 пакета.

## ADR-039. Полный набор токенов DESIGN.md в Tailwind v4 CSS-first
**Принято.** Продолжение ADR-024: в `apps/web/src/styles.css` объявлены цвета, шрифты, радиусы, тени, типографическая шкала (мобильная и `*-lg` для десктопа), контейнер 1200 px. Длительности движения, safe-area и z-index тоста оформлены как `@utility` (`duration-micro`, `duration-panel`, `duration-sheet`, `pt-safe`, `pb-safe`, `pb-nav`, `z-toast`), чтобы в компонентах не было магических значений. Светлая тема обязательна; тёмная остаётся в Сессии 16. Последствие: размеры заголовков задаются классами `text-h1 lg:text-h1-lg`, а не произвольными `text-[28px]`.

## ADR-040. Single-flight refresh в клиенте API
**Принято.** Пункт из Backlog Сессии 4 закрыт: `shared/api` при `401` запускает один общий `POST /auth/refresh` для всех параллельных запросов, ждёт его и повторяет исходные запросы. Auth-эндпоинты исключены, чтобы не зациклиться, а `GET /me` наоборот использует refresh: иначе после 15 минут жизни access-токена SPA выглядела бы разлогиненной до перезагрузки. Обновление сериализуется и между вкладками через Web Locks (`staynest-refresh`): cookie-jar и refresh-токен общие, поэтому два параллельных refresh из разных вкладок сервер принял бы за повторное использование и отозвал family; без Web Locks остаётся same-tab дедупликация. Результат refresh различает `ok`, `unauthenticated` (только 401/403) и `error` (сеть, 5xx, другие статусы). При `unauthenticated` клиент возвращает исходный 401, и `useMe` даёт `null`; при `error` выбрасывается ошибка refresh, и защищённый маршрут показывает «Не удалось проверить сессию», а не форму входа. Последствие: анонимный первый загруз делает один лишний запрос refresh; зато временный сбой API не выглядит как выход из аккаунта.

## ADR-041. В Сессии 4 добавлены страницы подтверждения email и сброса пароля
**Принято.** Письма Сессии 3 ведут на `/verify-email?token=...` и `/reset-password?token=...`, а текст письма «аккаунт уже существует» ссылается на «Забыли пароль» на странице входа. Без этих экранов регистрация в браузере упиралась бы в 404, поэтому в рамках auth-UI добавлены `/verify-email`, `/forgot-password`, `/reset-password`. Они используют общие схемы (`verifyEmailInputSchema`, `forgotPasswordInputSchema`, `resetPasswordInputSchema`) и не создают сессию: после подтверждения или сброса пользователь входит заново. Ответ на запрос сброса всегда одинаковый (`202`), как в ADR-033. Последствие: объём Сессии 4 вырос на три тонкие страницы; зато сквозной сценарий регистрации не имеет тупиков.

## ADR-042. Черновик объявления может быть недозаполнен, полнота проверяется CHECK-ом
**Принято.** Мастер Сессии 7 сохраняет объявление по шагам, поэтому `POST /listings` создаёт пустую строку. Миграция `0007_listing_drafts` снимает `NOT NULL` с `title`, `city`, `max_guests`, `bedrooms`, `beds`, `base_price_minor` и добавляет `CHECK listings_complete_when_not_draft`: всё, что не `draft`, обязано иметь полный набор полей. Проверка в приложении даёт `422 listing_incomplete` с `{field, code, message}` для UI, а CHECK остаётся последней линией защиты от прямых SQL-записей. Альтернатива с фиктивными значениями при создании отклонена: плейсхолдерная цена или название неотличимы от реальных и ломают публикацию. Последствие: откат миграции удаляет недозаполненные черновики, которые в старой схеме существовать не могли (задокументировано в `down`).

## ADR-043. Права и публикация объявления: ownership через 404 и список ошибок вместо одного текста
**Принято.** Все операции хозяина ищут строку по `(owner_id, id)`; чужая строка даёт `404 listing_not_found`, а не `403`, чтобы не раскрывать существование объявления. Публикация требует подтверждённый email при `REQUIRE_EMAIL_VERIFICATION=true`, минимум 3 фото, название 5–120, описание от 50, город, адрес, вместимость, спальни, кровати и цену. Ответ `422 listing_incomplete` содержит массив `{field, code, message}`: UI переводит `code` в i18n и делает ссылки к полям, не разбирая человеческий текст. Архивирование проверяет будущие активные брони чтением `bookings` (исключение из правила владения таблицей — read-only проверка). Повторная публикация из `archived` разрешена и обновляет `published_at`: хозяин может вернуть объявление в каталог без создания нового. Последствие: мастер и редактор не дублируют правила публикации, а показывают ответ сервера.

## ADR-044. Авторизация других модулей через публичный guard auth и фича `features/listings`
**Принято.** `modules/auth/index.ts` экспортирует `createAuthGuard({db, config})`; модуль `listings` не импортирует внутренности `auth` и не создаёт второй экземпляр сервиса авторизации. Гард проверяет access-токен и активную family так же, как `/me`. На фронте экран «Мои объявления» и черновик живут в `features/listings`; мастер Сессии 7 станет `features/listing-editor` и переиспользует API-контракты. Последствие: любой новый защищённый модуль подключает один и тот же guard, а не копирует проверку cookie.

## ADR-045. Изменения объявления выполняются в транзакции с блокировкой строки
**Принято.** `update`, `PUT amenities`, `publish`, `archive` и `DELETE` сначала делают `SELECT ... FROM listings WHERE id = $1 AND owner_id = $2 FOR UPDATE` внутри транзакции, затем проверяют статус, брони и полноту и только потом пишут. Это закрывает TOCTOU: параллельная бронь не проскочит между проверкой «нет будущих броней» и архивированием, а два одновременных `publish` дают ровно один `200` и один `409`. Событие `listing.published` публикуется после коммита. Публикация сначала проверяет владение и только потом email, поэтому чужое объявление остаётся `404`, а не превращается в `403`. Последствие: каждая запись держит короткую транзакцию; при появлении броней в Сессии 11 порядок блокировок совпадает с booking-engine (`listings` → `bookings`), что снижает риск дедлока.

## ADR-046. Длины текста в code points, потолок денег и единственная валюта MVP
**Принято.** JS `.length` считает UTF-16 code units, а PostgreSQL `char_length` — code points; из-за этого название из трёх emoji проходило zod, но нарушало CHECK и давало `500`. Общая функция `textLength` в `@staynest/shared` используется в zod-схемах, серверной проверке публикации и форме. Денежные поля ограничены `MAX_MONEY_MINOR` (1 млрд ₽), чтобы `bigint` не переполнялся; `currency` принимает только `RUB` до появления мультивалютности, `country` — две латинские буквы. Нарушение CHECK в БД преобразуется в `422 listing_incomplete`, а не в `500`. Клиентский `formatMoney` не падает на неизвестной валюте из старых данных. Последствие: при добавлении другой валюты нужно расширить enum, DTO и форматирование осознанно.

## ADR-047. Форматы фото: JPEG/PNG/WebP/AVIF, перекодировка из сырых пикселей
**Принято.** Формат определяется `file-type` по сигнатуре, имя файла и клиентский `Content-Type` игнорируются. Проходят JPEG, PNG, WebP и AVIF. HEIC не принимается: prebuilt-libvips в `sharp` 0.35 декодирует только AVIF (`heif` input с суффиксом `.avif`), а включение HEIC требует системного libheif с патентными ограничениями. iOS при выборе фото через `<input accept="image/*">` обычно отдаёт JPEG, а клиентский canvas всё равно конвертирует результат в WebP/JPEG. `sharp` вызывается с `limitInputPixels` (32 Мп по умолчанию, не больше 40 Мп через env) — защита от decompression bomb; ошибки декодирования дают `415`, превышение пикселей — `422`. После `rotate()` картинка декодируется в сырые RGBA и все три WebP-варианта собираются из них, поэтому EXIF (включая GPS), ICC и прочие метаданные не попадают в файлы. Альтернатива «отдавать оригинал как есть» отклонена: она сохраняет GPS и позволяет полиглотам. Последствие: HEIC-файл, попавший на сервер в обход браузера, получит понятный `415`.

## ADR-048. Хранилище: S3 SDK, бакет и публичная политика создаются API
**Принято.** Приложение работает с Silo/MinIO через `@aws-sdk/client-s3` с `forcePathStyle`. При первом обращении API идемпотентно создаёт бакет и ставит политику, разрешающую анонимный `GetObject` только на `listings/*/*/*.webp`; консоль и остальные объекты наружу не публикуются. В БД хранится только префикс, а ответы содержат относительные URL `/media/{prefix}/{variant}.webp`. В проде Caddy проксирует `/media/listings/*` в Silo только для `GET`/`HEAD`, с `nosniff` и `Cache-Control: immutable`, в dev то же делает Vite. Presigned URL отклонены: они истекают, мешают кэшу service worker (Сессия 15) и удлиняют ответы. Последствие: политика бакета живёт в коде и повторно применяется при старте; смена публичного префикса — через `MEDIA_PUBLIC_PATH`.

## ADR-049. Загрузка: multipart по файлу, клиентское сжатие, XHR для прогресса
**Принято.** `POST /listings/:id/photos` принимает multipart с полем `files` (до 10 файлов за запрос, 10 МБ каждый) и возвращает полный список фото. Клиент сжимает каждое фото в canvas до 2000 px и отправляет по одному файлу через `XMLHttpRequest`, потому что `fetch` не отдаёт прогресс отправки; `api.upload` повторяет запрос после single-flight refresh при `401`. Сервер читает части как async iterable, но слот семафора берётся до `toBuffer()`: пока задача ждёт очередь, в памяти нет даже исходного буфера. Внутри слота файл декодируется, три варианта сразу уходят в S3, и в памяти остаются только метаданные. При превышении лимита или исчезновении объявления уже загруженное удаляется. Порядок и обложка меняются отдельными идемпотентными PATCH-запросами. Последствие: при обрыве связи остаётся загруженный файл-сирота, его очищает Backlog-джоб; зато интерфейс показывает прогресс и не держит транзакцию на время работы sharp.

## ADR-050. Лимиты фото: 32 Мп по умолчанию, 30 загрузок за 10 минут, минимум 3 у published
**Принято.** `PHOTO_MAX_PIXELS` по умолчанию 32 Мп, схема env не принимает больше 40 Мп: 40 Мп RGBA — это ~160 МБ, а контейнер API ограничен 384 МБ. Загрузки сериализуются семафором на два одновременных вызова sharp внутри процесса и ограничены 30 запросами за 10 минут на пользователя (429 + `Retry-After`). Счётчик в памяти, как и auth rate limit (ADR-034), достаточен для одного инстанса; при масштабировании переносится в общее хранилище. У опубликованного объявления нельзя удалить фото, если останется меньше трёх: `422 photos_too_few_published`, транзакция откатывается. Альтернатива «переводить в draft» отклонена: хозяин не ожидает молчаливой смены статуса, а каталог не должен показывать неполную карточку. Последствия: HEIC и слишком большие файлы получают понятные коды; лимит по пользователю — Backlog для нескольких инстансов.

## ADR-051. Мастер объявления: localStorage-снимок и восстановление вместо версионирования API
**Принято.** Мастер Сессии 7 состоит из пяти шагов и сохраняет черновик через 900 мс после изменения: `PATCH /listings/:id`, затем `PUT /amenities`, если удобства менялись. Запросы сериализуются через цепочку промисов, поэтому ручная публикация не обгоняет автосохранение. Каждое изменение синхронно пишется в `localStorage` (`staynest:listing-draft:<id>`) вместе с шагом и `baseUpdatedAt`; при открытии страницы мастер продолжает с первого неполного шага, а несохранённый снимок восстанавливает. Если `updatedAt` на сервере новее базы снимка, показывается конфликт «оставить серверную версию / вернуть мои правки»; пока конфликт открыт, поля и сохранение заблокированы, чтобы новые правки не потерялись. Серверные `409` при публикации или архивировании тоже показываются отдельным баннером с обновлением списка. Публикация разрешена только после проверки всех шагов на клиенте и сохранения; серверный `422 listing_incomplete` переводит на нужный шаг. У `published`/`archived` автосохранения нет, но несохранённый снимок пишется в `localStorage` и восстанавливается при открытии, поэтому закрытие вкладки не теряет правки, а индикатор показывает «Есть несохранённые изменения». Альтернатива с `If-Match`/версией в API отклонена в рамках сессии: она требует менять контракт PATCH и схему ради сценария, который в MVP закрывается снимком и сравнением времени. Последствие: локальный снимок привязан к браузеру (на другом устройстве черновик откроется на первом неполном шаге с серверными данными), а конфликт после загрузки страницы ловится только при следующем открытии; одновременная правка в двух вкладках разрешается последней записью сервера. См. `apps/web/src/features/listing-editor/README.md`.

## ADR-052. Шаги мастера на мобильном показываются номерами
**Принято.** В `Stepper` подписи шагов скрываются на экранах уже `sm`, остаются номера и галочки, а полное название передаётся в `aria-label` кнопки. Причина: пять подписей не помещаются в 360 px и превращались в «Р», «Х», «Ц»; текущий шаг и так назван над прогресс-баром. На планшете и десктопе подписи видны. Последствие: визуальная плотность лучше, доступное имя шага не теряется.

## ADR-053. Публичный каталог — отдельная read-модель с отдельным DTO
**Принято.** Сессия 8 добавляет `modules/catalog` (только чтение `listings`, `listing_photos`, `listing_amenities`, `amenities`, как разрешено ADR-017) и `features/catalog`. Публичная выдача использует `PublicListingSummary` для списка и `PublicListing` для карточки; в них нет `addressLine`, точных `lat`/`lng`, `ownerId`, `status` и `pendingBookingsCount`. Вместо координат отдаются `approxLat`/`approxLng`, округлённые до 0.01° (~1 км). `GET /listings/:id` ищет только `published`, черновик и архив дают `404 listing_not_found`. Последствие: owner-only `ListingDto` из Сессии 5 не переиспользуется в публичном контракте, поэтому приватные поля нельзя случайно вернуть. Точный адрес появится только в брони после подтверждения (Сессия 12). Маппинг фото и удобств в `catalog` дублируется с `listings`; это цена независимых контрактов, общий маппер преждевременен.

## ADR-054. Курсорная пагинация каталога по кортежу сортировки
**Принято.** Курсор — base64url от JSON `{v, sort, id, ...}`. Время в курсоре — строка `to_char(published_at ... 'US')` с микросекундами, потому что `Date.toISOString()` их теряет и на сидах через `now()` теряет строки. Для `newest` сравнивается `(published_at, id)`, для цены — `(base_price_minor, id)`, для релевантности — `(rank, published_at, id)`. `id` делает порядок строгим, поэтому одинаковые цена или ранг не дают дублей и пропусков. `ts_rank_cd` возвращает `real`; в SELECT, ORDER BY и WHERE он приводится к `float8`, иначе `pg` отдаёт в JS округлённое значение, а Postgres сравнивает его с полной точностью `real`, и следующая страница оказывается пустой. Курсор другой сортировки, другой `q` в релевантности или битый JSON даёт `400 invalid_cursor`. Последствие: курсор не попадает в URL — ссылка воспроизводит фильтры, а не позицию прокрутки; курсор не содержит хэш фильтров, поэтому клиент обязан сбрасывать его при изменении фильтров (UI делает это через ключ TanStack Query).

## ADR-055. Состояние каталога в URL и подсказки города через datalist
**Принято.** Фильтры живут в query-параметрах под именами API (`q`, `city`, `guests`, `priceMin`, `priceMax`, `bedroomsMin`, `type`, `amenities`, `sort`). Цены в URL и API — в копейках, а поля фильтра показывают рубли (`minorToInput`/`inputToMinor`). Для совместимости с ТЗ API принимает и `price_min`, `price_max`, `bedrooms_min`, `type[]`, `amenities[]`; повторяющиеся значения дедуплицируются. Парсер отбрасывает невалидные значения, поэтому испорченная ссылка не ломает экран. `relevance` включается только при непустом `q`, иначе эффективной сортировкой становится `newest`. Подсказки города приходят из `GET /cities` (до восьми самых частых опубликованных городов) и показываются нативным `datalist`; запрос уходит после двух символов, ввод откладывается через `useDeferredValue`. Последствие: URL можно отправлять и открывать без потери фильтров, но позиция бесконечной прокрутки не сохраняется. Нативный `datalist` доступен с клавиатуры и не тянет новую зависимость, но его оформление зависит от браузера.

## ADR-056. Цены считает чистая функция, приоритет сезонных правил детерминирован
**Принято.** Расчёт вынесен в `modules/pricing/calculator.ts` — чистую функцию без БД и `Date`: сервис передаёт ей базовые цены, правила, занятые ночи и строку «сегодня». Для каждой ночи выбирается правило с максимальным `priority`; при равенстве — с более поздней `dateFrom`; при полном совпадении периода — с меньшим `id`. Иначе один и тот же набор правил мог бы давать разную цену в зависимости от порядка строк. Сезонная цена важнее выходной, выходная важнее базовой. `min_nights` берётся как максимум из `listings.min_nights` и правил, которые выиграли цену хотя бы на одной ночи: низкоприоритетное правило не может незаметно удлинить срок. Уборка добавляется один раз, сервисный сбор в MVP равен нулю, но остаётся в `price_breakdown`. «Сегодня» считается в `LISTING_TIME_ZONE` (по умолчанию `Europe/Moscow`) через `Intl`, а не по часам сервера или браузера. Последствие: для нескольких таймзон понадобится поле у объявления, но в MVP одна зона на инстанс.

## ADR-057. Quote отдаёт сервер, клиент не складывает деньги
**Принято.** `GET /listings/:id/quote` возвращает ночи с источником цены (`seasonal`/`weekend`/`base`), группы одинаковых цен, уборку, сервисный сбор и итог. Клиент показывает эти числа как есть и не пересчитывает сумму: иначе округление или устаревшая цена дадут расхождение с сервером. До запроса клиент проверяет только правила, которые знает из календаря (минимальный и максимальный срок, занятые ночи), чтобы не показывать заведомую ошибку. Ошибки расчёта — `422` для правил и `409 dates_unavailable` для занятости; в `errors[]` передаётся `minNights`, чтобы UI перевёл код, а не показывал русский текст сервера в английской локали. Ответ quote — `Cache-Control: private, no-store`, потому что цена и занятость должны быть свежими. Последствие: один дополнительный запрос на каждое изменение диапазона или числа гостей; сумма в интерфейсе всегда совпадает с сервером.

## ADR-058. Блокировки дат включительны в API и полуинтервальны в БД
**Принято.** Хозяин в интерфейсе выбирает заезд и выезд, как гость; реально блокируются ночи с `dateFrom` по `dateTo = выезд - 1` включительно. API принимает последнюю ночь включительно и хранит `block_range = [dateFrom, dateTo + 1)`, как и бронь `[check_in, check_out)`. В `BlockDto` возвращается снова включительная `dateTo`, а публичный календарь отдаёт плоский список ночей `{date, kind}`, поэтому клиенту не нужно помнить семантику границ. Одна блокировка ограничена 366 ночами, причина — 200 символами: иначе публичный календарь разворачивал бы блок на тысячи лет. Блокировка в прошлом — `422 block_in_past`; пересечение с активной бронью — `409 block_overlaps_booking`; пересечение с блокировкой — `409 block_overlaps`, плюс EXCLUDE-ограничение как последняя линия защиты. Создание блока берёт `FOR UPDATE` на объявление — та же блокировка, что будет в движке бронирования Сессии 11. Последствие: в БД и API две разные семантики границ, это зафиксировано в контракте и тестах.

## ADR-059. Календарь на react-day-picker v10 с собственной логикой диапазона
**Принято.** Добавлен `react-day-picker@10.0.2` (пин, тянет `date-fns` v4) — библиотека из ТЗ, с локалями ru/en и доступной сеткой дней. Стандартный CSS не подключён: элементы оформлены Tailwind-классами из `shared/ui/calendarStyles.ts` через токены DESIGN.md. Встроенный `excludeDisabled` не подходит, потому что дата выезда может совпадать с занятой ночью следующего гостя: если пометить её `disabled`, этот сценарий станет невозможен. Поэтому занятые ночи только подсвечиваются, а `selectRange` в `features/booking/model/selection.ts` проверяет ночи `[from, clicked)` и при попытке перепрыгнуть занятую ночь переносит начало выбора. Каждая ячейка получает `aria-label` «дата, статус»; статусы выводятся текстом, не только цветом. Тяжёлые маршруты (каталог, карточка с календарём, мастер, календарь хозяина) вынесены в lazy-чанки: основной бандл уменьшился примерно с 313 до 195 kB gzip. Последствие: в jsdom ленивые маршруты грузятся дольше секунды, поэтому `asyncUtilTimeout` в тестах поднят до 10 с.



## ADR-060. Поиск по датам и итог за период: доступность в SQL, цена в общем чистом ядре
**Принято.** В Сессии 10 `GET /listings` принимает `check_in`/`check_out` (и camelCase), требует обе даты, проверяет порядок и предел 365 ночей. Доступность считается подзапросами `NOT EXISTS` по `bookings` со статусами `pending`/`confirmed` и по `listing_blocks`, с `daterange(..., '[)')`: смежные заезды не пересекаются, дом с бронью `[10,12)` доступен для `[12,14)`. Это тот же запрос, что в `DB.md`, раздел 18; на 10 000 объявлений он опирается на gist-индексы EXCLUDE-ограничений. Даты в выдаче только фильтруют, но не резервируют.

Если даты переданы, каждая карточка получает `stayPrice` (`nights`, `nightlyTotalMinor`, `cleaningFeeMinor`, `totalMinor`, `currency`). Расчёт вынесен в `packages/shared/src/stay-price.ts` — чистое ядро без БД и `Date`, которое используют и `/quote` (модуль `pricing`), и каталог. Это исключает расхождение суммы в карточке и при бронировании: приоритет сезонных правил, выходные и уборка считаются один раз. Каталог загружает правила цен для страницы одним запросом (read-only, ADR-017). `min_nights` и `max_nights` в поиске не фильтруются: выдача отвечает на вопрос «свободно ли», а окончательную проверку срока делает `/quote` и движок бронирования; клиент показывает итог, но не обещает бронируемость. Даты в прошлом каталог тоже не отклоняет — поиск не создаёт бронь; `/quote` отвечает `stay_in_past`. Альтернатива — повторять все правила брони в SQL каталога — отклонена: она дублирует валидацию и цену, а Backlog фиксирует подсказку «минимум N ночей» для С12.

Фильтр `price_min`/`price_max` по-прежнему ограничивает `base_price_minor` за ночь (FR-S2). Итог за период может быть выше из-за выходных, сезонных правил и уборки; карточка показывает реальную сумму, а не обещание фильтра. Альтернатива — считать цену в SQL и фильтровать по итогу периода — отклонена: дублирование правил ценообразования в SQL и потеря объяснимости. Последствие: один дополнительный запрос правил на страницу каталога (только при датах), зато одна реализация цены.

## ADR-061. Перф-поиска: функциональный индекс города, материализованный `busy` и двухэтапная релевантность
**Принято.** Миграция `0008` заменяет `(city, base_price_minor)` на функциональные индексы `(lower(city), base_price_minor)` и `(lower(city), published_at DESC, id DESC)` с условием `status = 'published'`: фильтр сравнивает `lower(city)`, и обычный индекс по `city` планировщик не использовал. Занятые дома собираются в материализованный CTE `busy` (активные брони + блокировки), чтобы планировщик стабильно делал hash anti join, а не коррелированный `NOT EXISTS`: без этого на `q`, совпадающем со всем каталогом, план прыгал между 28 и 197 мс. Релевантность дополнительно разделена на top-N по `(rank, published_at, id)` и join полных строк по PK. Итог на 10 000 объявлений/100 000 броней: worst p95 44 мс SQL и 85.2 мс HTTP (было 300 мс). Перф-данные (`scripts/seed-perf.mjs`) и замеры (`scripts/perf-search.mjs`, `scripts/perf-http.mjs`) воспроизводимы; результаты и планы — `docs/perf/search.md`. DoD — p95 < 150 мс, фактический худший p95 — 85.2 мс. Альтернатива с материализованным ранжированием или отдельным поисковым движком отклонена для MVP: данных и Postgres достаточно, а сложность инфраструктуры не оправдана. Последствие: `newest` с датами платит ~10 мс за построение `busy`; при росте каталога следующий шаг — narrow-выборка `id` для всех сортировок (Backlog).

## ADR-062. Движок бронирования: транзакция с блокировкой пользователя и объявления
**Принято.** `POST /bookings` выполняется в одной транзакции: `pg_advisory_xact_lock` по ключу идемпотентности → `SELECT users FOR UPDATE` → проверка лимита pending и email → `SELECT listings FOR UPDATE` → истечение просроченных `pending` этого объявления → расчёт цены внутри транзакции → `INSERT bookings` → `booking_events` → сохранение ответа идемпотентности. Если worker отстал, просроченная `pending` не блокирует новые даты: календарь, quote и каталог фильтруют её по `expires_at`, а создание брони переводит в `expired` под блокировкой объявления до quote. Порядок блокировок `users → listings → bookings` совпадает с `availability` и `listings` (ADR-045), что снижает риск дедлоков. Блокировка пользователя делает лимит «не более 5 pending» точным даже при параллельных заявках на разные дома; блокировка объявления сериализует конкурентов на одни даты. Exclusion constraint `bookings_no_overlap` остаётся последней линией защиты, а `23P01` и конфликт из quote превращаются в `409 booking_dates_unavailable`. Миграция `0009` запрещает бесконечные `daterange` (`NOT lower_inf AND NOT upper_inf`) и фиксирует форму `[)`; PostgreSQL и так канонизирует дискретный `daterange`, поэтому CHECK — контракт для будущих изменений типа. Последствие: транзакция держит две строки на время quote-запросов; это доли миллисекунды на MVP-данных.

## ADR-063. Идемпотентность через advisory lock и сохранение успешного ответа
**Принято.** Ключ `Idempotency-Key` обязателен для `POST /bookings` (8–200 символов `[A-Za-z0-9._:-]`). Хэш — SHA-256 от endpoint и нормализованного тела (ключи отсортированы). В начале транзакции берётся `pg_advisory_xact_lock(hashtextextended(user_id || ':' || key, 0))`, затем читается `idempotency_keys`: без advisory lock два параллельных запроса с одним ключом оба увидели бы «ключа нет» и создали две брони. Успешный `201` вместе с телом сохраняется в той же транзакции; повтор возвращает исходный статус/тело и `Idempotency-Replayed: true`, а другое тело с тем же ключом даёт `422 idempotency_key_conflict`. Rate limit проверяется после replay-проверки, поэтому повтор успешного запроса не получает 429. Ошибки (409/422) не сохраняются: транзакция откатывается, и повтор после освобождения дат должен иметь шанс выполниться. Альтернатива «сохранять любой ответ» отклонена: старый 409 навсегда привязал бы ключ к неудачной попытке. Последствие: ключ без успешного ответа можно переиспользовать с другим телом; это осознанно и задокументировано в `docs/booking-engine.md`.

## ADR-064. Машина состояний брони — чистая таблица переходов
**Принято.** `modules/bookings/state-machine.ts` содержит таблицу `action × status × role` без БД и HTTP. `confirm`/`decline` доступны только хозяину и только из `pending`; `cancel` из `pending` — только гостю (отказ хозяина оформляется как `decline`), из `confirmed` — гостю до даты заезда или хозяину с обязательной причиной. Любой другой переход — `409 invalid_booking_transition`. Если `pending` уже истёк по `expires_at`, действие под той же блокировкой сначала переводит бронь в `expired` (джоб может отставать), а клиент получает 409. Смена статуса идёт под `SELECT ... FOR UPDATE` брони, поэтому confirm и cancel не могут примениться к одному исходному статусу: проигравший видит новый статус и получает 409 (если действие всё ещё допустимо, например guest cancel после confirm, оно выполняется последовательно). Чужая бронь даёт `404 booking_not_found`, а не 403, чтобы не раскрывать существование. Гость, пытающийся подтвердить свою же заявку, получает `403 booking_action_forbidden`: он и так знает о брони. DTO отдаёт роли (`actorRole`, `cancelledByRole`), а не UUID пользователей. Последствие: таблица из 42 комбинаций покрыта unit-тестом, а UI Сессии 12 показывает только разрешённые действия.

## ADR-065. Фоновые задачи на pg-boss в отдельном worker-процессе
**Принято.** Добавлен `pg-boss` и процесс `apps/api/src/worker.ts` (`dist/worker.js`), API фоновые задачи не запускает. Очереди: `bookings.expire-pending` (каждую минуту), `bookings.complete-past` (00:15 по `LISTING_TIME_ZONE`), `bookings.cleanup-idempotency` (03:30). Задачи берут до 100 строк `FOR UPDATE SKIP LOCKED`, поэтому несколько воркеров не обрабатывают одну бронь, а confirm/decline не проигрывают гонку истечению. Схема `pgboss` создаётся и мигрируется самим pg-boss при старте, в доменных миграциях её нет. В `infra/docker-compose.prod.yml` worker использует тот же образ, что API, с `command: node dist/worker.js`. Альтернатива «setInterval в API» отклонена: при нескольких инстансах задачи дублировались бы, а падение API останавливало бы истечение. Последствия: на staging появился ещё один контейнер (192 МБ), а `pg_dump` должен включать схему `pgboss` вместе с `public`.

## ADR-066. Лимиты бронирования: БД для pending, память для rate limit
**Принято.** Лимит активных `pending` (по умолчанию 5) считается SQL-запросом под `SELECT users FOR UPDATE`, поэтому он точен между инстансами и не обходится параллельными запросами. Rate limit создания брони (по умолчанию 10 за 10 минут) использует тот же `FixedWindowRateLimiter`, что auth (ADR-034), и живёт в памяти процесса: при одном инстансе этого достаточно, при масштабировании счётчики переносятся в общее хранилище (Backlog). Требование подтверждённого email проверяется в транзакции по флагу `REQUIRE_EMAIL_VERIFICATION`. Последствие: жёсткий лимит pending можно обойти, только создав несколько аккаунтов; rate limit смягчает и это.

## ADR-067. UI бронирования: общий слой запросов, вкладки на клиенте, ключ идемпотентности по телу формы
**Принято.** Сессия 12 добавляет `features/booking` с общими API-вызовами, хуками TanStack Query и переиспользуемыми компонентами для гостя и хозяина. `GET /me/bookings` принимает только один `status`, поэтому «Мои поездки» и «Входящие заявки» загружают страницы через `useInfiniteQuery` без фильтра и группируют статусы на клиенте: «Предстоящие» — `pending`+`confirmed`, «Прошлые» — `completed`, «Отменённые» — остальные; у хозяина «Новые», «Подтверждённые», «Завершённые» и «Закрытые». Альтернатива из четырёх запросов на вкладку дала бы дубли и лишние round-trip. `Idempotency-Key` генерируется один раз на нормализованное тело формы (даты, гости, сообщение) и пересоздаётся при любом изменении: повтор после сетевой ошибки безопасен, а изменённая форма не получает `422 idempotency_key_conflict`. После успеха клиент открывает `/bookings/:id?created=1`; страница всегда делает `GET /bookings/:id`, поэтому replay не показывает устаревший снимок. После любой мутации инвалидируются `['bookings']`, `['booking']` и `['host-calendar']`, чтобы календарь и списки не расходились. Последствие: при большом числе броней клиент группирует только загруженные страницы; серверный мультистатус — Backlog.

## ADR-068. Адрес и телефон второй стороны открываются только после подтверждения
**Принято.** `BookingDetail` получает поле `contacts` (`addressLine`, `hostPhone`, `guestPhone`). Оно `null`, пока бронь не в статусе `confirmed` или `completed`. В подтверждённой брони гость видит точный адрес и телефон хозяина, хозяин — адрес и телефон гостя; вторая сторона не получает чужой телефон. Данные берутся из `listings.address_line` и `users.phone` в том же запросе, доступ проверяется существующим `findBookingForActor` (участник или 404). Публичная карточка по-прежнему не отдаёт точный адрес (ADR-053). Последствие: телефон может быть не заполнен — UI честно показывает «не указан»; форма редактирования телефона появится в профиле С14. Тест проверяет, что до подтверждения `contacts` равно `null`, а после — роль-специфичные поля.

## ADR-069. E2E на Playwright с отдельной тестовой базой и фикстурой фото через SQL
**Принято.** Добавлен `@playwright/test` и `playwright.config.ts`. Playwright сам поднимает API (`tsx src/server.ts`, `API_HOST=127.0.0.1`) и Vite; подготовка базы вынесена в явную команду `pnpm e2e:prepare`, которая требует `E2E_DATABASE_URL`, проверяет суффикс `_test` и loopback-хост и только затем делает `DROP SCHEMA`/миграции на `staynest_e2e_test`. Обычный `pnpm e2e` базу не трогает: `globalSetup` лишь проверяет наличие таблицы `users` и подсказывает команду подготовки. Локально Postgres берётся из `infra/docker-compose.dev.yml`, в CI — из сервиса `postgres:16`. Сценарий: API регистрирует хозяина, создаёт и публикует дом, затем браузерные контексты хозяина и гостя проходят UI-путь «вход → выбор дат → заявка → подтверждение → статус у гостя». Три фото вставляются в `listing_photos` через SQL: e2e проверяет бронирование, а не загрузчик (для загрузчика остаётся отдельный Backlog-сценарий); URL фото может отдавать 404, тест это не проверяет. `webServer` задаёт `REQUIRE_EMAIL_VERIFICATION=false`, иначе регистрация в e2e требовала бы почту. В Сессии 13 сценарий дополнен колокольчиком: после заявки у хозяина появляется unread-счётчик, а после подтверждения гость получает уведомление по SSE без перезагрузки. CI-job `e2e` ставит Chromium, выполняет `pnpm e2e:prepare`, запускает тест и сохраняет отчёт при падении на 3 дня. Последствие: e2e требует доступного Postgres; параллельный запуск с API-тестами на одной базе запрещён — используется отдельное имя `staynest_e2e_test`.

## ADR-070. Уведомления: единый сервис, SSE-hub в памяти и устойчивый список
**Принято.** `modules/notifications` — единственная точка создания уведомлений: пишет строку в `notifications`, отдаёт её подписчикам SSE и отправляет push. События брони приходят через `EventBus`; API создаёт сервис в своих роутах, worker — в процессе фоновых задач, поэтому `booking.expired`/`booking.completed` тоже оставляют in-app след. Список уведомлений — источник истины: `GET /me/notifications` с курсором `(created_at, id)` и `unreadCount`, а SSE нужен только для мгновенности. Hub держит до пяти потоков на пользователя в памяти; клиент дополнительно опрашивает список раз в 60 секунд и перезапрашивает его при переподключении через инвалидацию TanStack Query, поэтому пропущенные события не теряются. Альтернатива с хранением каждого события в отдельном журнале и replay по `Last-Event-ID` отклонена для MVP: она дублирует уже сохранённые уведомления. Последствие: при нескольких инстансах API или событиях из worker нужен общий broker (Postgres LISTEN/NOTIFY/Redis) — записано в Backlog. Клиент дополнительно опрашивает список раз в 60 секунд, поэтому тихое обновление не зависит от жизни SSE.

## ADR-071. Web Push: VAPID из окружения, upsert endpoint и минимальный service worker
**Принято.** Пара `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY` генерируется `pnpm vapid:generate` и живёт только в `.env`; без неё push выключен, а `GET /me/push/config` возвращает `enabled:false`, `POST /me/push-subscriptions` — `503 push_not_configured`. Браузер получает публичный ключ при входе в профиль, разрешение запрашивается только по клику. Endpoint уникален глобально: `ON CONFLICT (endpoint) DO UPDATE SET user_id = ...` перепривязывает подписку при смене пользователя на устройстве, а `DELETE` фильтрует по `user_id`. Ответы push-сервиса `404/410` удаляют мёртвую строку; успешная отправка обновляет `last_used_at`. Отправка ограничена allowlist-хостами известных push-сервисов; неподдерживаемый endpoint отклоняется уже на `POST /me/push-subscriptions` (`422 push_host_not_allowed`), а сам запрос имеет таймаут 10 с, чтобы подписка на произвольный https-адрес не превращала API в SSRF-сканер. Браузер запоминает `staynest:push-owner` в localStorage: при входе другого аккаунта в том же браузере старая подписка отписывается (иначе чужому пользователю продолжали бы приходить имена гостей и названия домов). Добавлена зависимость `web-push` (проверенная библиотека с VAPID и шифрованием payload) и `@types/web-push`. Для приёма push зарегистрирован минимальный `public/sw.js` только с обработчиками `push` и `notificationclick`; URL клика ограничен своим origin и путём. Полноценный Workbox — Сессия 15, до неё кэширование не включается, чтобы не конфликтовать с будущим service worker. Последствие: push не работает без HTTPS/установленного PWA на iOS; UI честно объясняет отказ и отсутствие VAPID. Реальная доставка на телефон требует ручной проверки — в CI headless Chromium не выдаёт разрешение, API-тесты используют фейковый sender.

## ADR-072. Событие брони несёт данные для уведомлений
**Принято.** `BookingEventPayload` расширен `listingTitle`, `checkIn`, `checkOut`, `guestName`, `totalMinor`, `currency` и опциональным `expiresAt`. Эти поля заполняются в `create`, `transition`, `jobs` и `expiry` (данные уже есть в `BookingDetailRow`/`JobBookingRow`). `notifications` не делает SQL-соединений с `bookings`/`listings`: по ADR-017 это нарушило бы границы модулей, а отдельный read-only контракт ради четырёх строк преждевременен. Локаль получателя берётся через публичный `usersService`, таблица `users` принадлежит модулю users. Последствие: событие стало шире, зато подписчики не зависят от схемы броней и могут добавляться без новых запросов в горячем пути.

## ADR-073. Напоминание об истечении заявки дедуплицируется уникальным ключом
**Принято.** Джоб `bookings.expiring-soon` каждые 10 минут публикует `booking.expiring_soon` для `pending`, попадающих в окно `BOOKING_EXPIRY_WARNING_HOURS` (3). Он не меняет бронь и не берёт блокировок. `notifications` добавляет `dedupe_key` и частичный уникальный индекс `(user_id, dedupe_key) WHERE dedupe_key IS NOT NULL`; для напоминания ключ `expiring:<booking_id>`. `INSERT ... ON CONFLICT DO NOTHING` возвращает строку только при первом срабатывании, поэтому push не дублируется. Альтернатива с проверкой существующей строки перед вставкой имела гонку при нескольких воркерах. Последствие: миграция `0010`; при повторном запуске джоба число событий остаётся прежним, это проверяет тест.

## ADR-074. Клиент SSE использует fetch, а не EventSource
**Принято.** `GET /me/events` авторизуется httpOnly cookie, но native `EventSource` не умеет обновлять истёкший access-токен и при 401 начинает бесконечные повторы. Клиент читает поток через `fetch` + `ReadableStream`: при 401 вызывает тот же single-flight refresh, что и обычные запросы (ADR-040), затем переподключается; при 4xx (кроме 401) останавливается, при сети/5xx делает экспоненциальную паузу до 30 секунд. Сервер шлёт `retry: 3000`, heartbeat `: ping` раз в 25 секунд и `event: notification` с `id`. Caddy для этого пути отключает буферизацию (`flush_interval -1`), API отдаёт `X-Accel-Buffering: no`. Последствие: SSE-код живёт в `shared/api/stream.ts`, а не в компоненте; тест поднимает реальный HTTP-сервер и проверяет формат потока.
