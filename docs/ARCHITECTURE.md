# ARCHITECTURE: как код разбит на блоки

## 1. Принцип
**Модульный монолит.** Одно приложение и одна база, но код разделён на независимые модули с чёткими границами. Каждый модуль отвечает за одну область (дома, участники, бронирование...), хранит свою логику и свои запросы и общается с другими только через публичный интерфейс.

Почему не одно полотно: правки в одном месте ломают другое, ревью и тесты превращаются в хаос, нельзя понять, где что лежит.
Почему не микросервисы: для одного VPS и одного разработчика это лишняя сложность (сеть, деплой, распределённые транзакции). Модульный монолит даёт 90% пользы, а при росте любой модуль можно вынести в отдельный сервис, потому что границы уже проведены.

## 2. Карта блоков

| Блок (как ты его называешь) | Модуль бэкенда `apps/api/src/modules/` | Фича фронтенда `apps/web/src/features/` | Таблицы (владелец) |
|---|---|---|---|
| **Участники** (аккаунты, профиль) | `auth`, `users`, `telegram` | `auth`, `profile`, `mode-switch`, `telegram` | `users`, `refresh_tokens`, `auth_tokens`, `telegram_identities` |
| **Дома** (объявления) | `listings` | `listings` (мои объявления и черновик), `listing-editor` (мастер, Сессия 7), `listing-details` | `listings`, `listing_amenities`, `amenities` |
| Фото домов | `photos` | `photo-uploader`, `photo-gallery` | `listing_photos` |
| Цены | `pricing` | `price-editor` | `listing_price_rules` |
| Доступность и календарь | `availability` | `calendar` | `listing_blocks` |
| **Главная и каталог** | `catalog` (только чтение) | `catalog`, `filters` | читает `listings`, `bookings` |
| Бронирование | `bookings` (включая депозиты) | `booking`, `trips`, `host-requests` | `bookings`, `booking_events`, `idempotency_keys`, `payments` |
| Уведомления | `notifications` | `notifications` | `notifications`, `push_subscriptions` |
| Избранное | `favorites` | `favorites` | `favorites` |
| Панель хозяина | `dashboard` (только чтение) | `host-dashboard` | читает `bookings`, `listings` |
| Платформа (общее ядро) | `platform` (config, db, logger, errors, http, mailer, events) | `shared/` | нет |

**Главная страница** это не модуль с логикой, а страница-сборщик: `pages/home` собирает фичи `catalog`, `filters` и т.д. Страницы тонкие, логика живёт в фичах.

Правило владения: **таблицей владеет один модуль**. Только он пишет в неё. Другие модули читают через его публичные функции. Единственное исключение, зафиксированное в ADR-017: `catalog` и `dashboard` это read-модели, которые для скорости делают SQL-соединения по таблицам других модулей и ничего в них не пишут.

## 3. Бэкенд: структура

```
apps/api/src/
├─ app.ts                 сборка Fastify: плагины, регистрация модулей
├─ server.ts              запуск
├─ worker.ts              запуск фоновых задач (pg-boss)
├─ platform/              общее ядро (не бизнес-логика)
│  ├─ config/  db/  logger/  errors/  http/  mailer/  events/  jobs/
└─ modules/
   ├─ auth/
   │  ├─ index.ts         ПУБЛИЧНЫЙ интерфейс модуля (только то, что можно использовать снаружи)
   │  ├─ routes.ts        HTTP: разбор запроса, вызов сервиса, ответ. Без бизнес-логики
   │  ├─ service.ts       бизнес-логика, правила, транзакции
   │  ├─ repo.ts          SQL-запросы (Kysely). Только здесь есть работа с БД
   │  ├─ schemas.ts       zod-схемы входа и выхода (контракт, общий с фронтом через packages/shared)
   │  ├─ events.ts        события, которые модуль публикует и на которые подписан
   │  ├─ README.md        зачем модуль, публичный API, таблицы, события, как тестировать
   │  └─ *.test.ts        тесты рядом с кодом
   ├─ listings/  photos/  pricing/  availability/
   ├─ catalog/  bookings/  notifications/  favorites/  dashboard/  profile/  users/
```

Слои внутри модуля: `routes → service → repo`. Вниз можно, вверх нельзя. `routes` не ходит в БД, `repo` не знает про HTTP.

### Правила зависимостей
```mermaid
flowchart TD
  R[routes] --> S[service]
  S --> P[repo]
  S -. только через index.ts .-> OM[другой модуль]
  S --> PL[platform]
  P --> PL
  OM --> PL
```
1. Из модуля A в модуль B можно импортировать **только `modules/B/index.ts`**. Импорт `modules/B/repo.ts` или `service.ts` запрещён (ломает линт и CI).
2. `platform` не импортирует модули.
3. Циклические зависимости между модулями запрещены. Если A и B нужны друг другу, это сигнал, что нужно событие (раздел 5) или третий модуль.
4. Транзакции передаются явно параметром `trx`. Модуль не открывает транзакцию внутри чужой. Пример: `bookings` открывает транзакцию и вызывает `listings.lockForBooking(trx, listingId)`.
5. Чистая бизнес-логика (расчёт цен, машина состояний) лежит в отдельных файлах без БД (`pricing.ts`, `state-machine.ts`) и тестируется без инфраструктуры.

## 4. Фронтенд: структура

```
apps/web/src/
├─ app/                   провайдеры, роутер, макет, lazyPages, ErrorBoundary, регистрация service worker
├─ pages/                 экраны уровня маршрута, ТОНКИЕ: собирают фичи
│  ├─ home/  listing/  host-dashboard/  host-listings/  host-requests/  host-calendar/
│  ├─ trips/  favorites/  profile/  login/  offline/  not-found/
├─ features/              законченные пользовательские блоки
│  ├─ pwa/                service worker, офлайн-баннеры, установка, очистка кэшей
│  └─ catalog/
│     ├─ index.ts         публичный интерфейс фичи (компоненты и хуки, доступные снаружи)
│     ├─ api/             запросы и хуки TanStack Query
│     ├─ components/      компоненты фичи
│     ├─ model/           состояние, хуки, чистая логика (парсинг фильтров URL и т.д.)
│     ├─ README.md
│     └─ *.test.tsx
└─ shared/
   ├─ ui/                 компоненты дизайн-системы (Button, Input, Modal...), без бизнес-логики
   ├─ api/                клиент API, обработка problem+json
   ├─ lib/                утилиты (даты, деньги, форматирование)
   ├─ i18n/               ключи и инициализация
   └─ config/
```

Правила:
1. `shared` не импортирует `features` и `pages`. `features` не импортируют `pages`.
2. Фича не импортирует внутренности другой фичи, только её `index.ts`. Если две фичи сильно связаны, общий кусок поднимается в `shared` или одна фича композирует другую на уровне страницы.
3. Страница не содержит логики запросов и бизнес-правил, только композицию.
4. Состояние сервера только через TanStack Query. Глобального состояния минимум (текущий пользователь, режим, тема).
5. Контракты запросов и ответов берутся из `packages/shared` (общие zod-схемы), а не описываются дважды.

## 5. События между модулями (внутренний event bus)

Чтобы `bookings` не знал про `notifications`, модули общаются событиями внутри процесса (типизированный эмиттер в `platform/events`). Публикация **после коммита транзакции**.

| Событие | Публикует | Подписаны |
|---|---|---|
| `user.registered` | `auth` | пока никто; письмо подтверждения `auth` отправляет сам через `mailer` |
| `booking.requested` | `bookings` | `notifications` (хозяину) |
| `booking.confirmed` / `booking.declined` | `bookings` | `notifications` (гостю) |
| `booking.cancelled` | `bookings` | `notifications` (второй стороне) |
| `booking.expired` | `bookings` (джоб или истечение под блокировкой) | `notifications` (гостю) |
| `booking.deposit_expired` | `bookings` (джоб депозита) | `notifications` (гостю и хозяину) |
| `booking.expiring_soon` | `bookings` (джоб) | `notifications` (хозяину, дедупликация) |
| `booking.completed` | `bookings` (джоб) | `notifications` (гостю), `dashboard` (при необходимости кэша) |
| `listing.published` | `listings` | пока никто (задел) |

События `booking.*` несут готовые поля для уведомлений (`listingTitle`, даты, имя гостя, сумма), поэтому `notifications` не читает таблицы броней (ADR-072). Доставка в SSE-хаб живёт в памяти процесса; повторная доставка через pg-boss и общий broker для нескольких инстансов — Backlog (ADR-070).

## 6. Ограничения размера и сложности (проверяет линтер и CI)

| Правило | Лимит |
|---|---|
| Строк в файле | 300 (исключения только с комментарием причины) |
| Строк в функции | 60 |
| Цикломатическая сложность | 12 |
| Строк в React-компоненте | 200 |
| Параметров функции | 4 (дальше объект) |
| Вложенность | 4 уровня |

Инструменты:
- ESLint: `max-lines`, `max-lines-per-function`, `complexity`, `max-params`, `max-depth`, запрет `eval` и `dangerouslySetInnerHTML`.
- Границы модулей проверяет dependency-cruiser (`pnpm depcheck`): запрет циклов, импорт чужого модуля только через `index.ts`, `platform` не зависит от `modules`, `shared` не зависит от `features`. Отдельный плагин boundaries не добавляется, чтобы не тянуть лишнюю зависимость; правило проверено тестом с временным глубоким импортом.
- **dependency-cruiser** в CI: правила "нет циклов", "модуль импортирует только index.ts другого модуля", "platform не зависит от modules", "shared не зависит от features". Граф зависимостей кладётся в `docs/architecture/deps.svg` (сильная иллюстрация для кейса).
- `knip`: поиск мёртвого кода и неиспользуемых экспортов.

## 7. Как добавлять новую функцию (чек-лист)
1. Определи, к какому модулю или фиче она относится. Если ни к какому, создай новый модуль по шаблону (навык `module-architecture`).
2. Контракт: zod-схемы в `packages/shared`.
3. БД: миграция (навык `db-migrations`), владелец таблицы указан в `DB.md`.
4. Бэкенд: `repo` → `service` → `routes`, затем экспорт в `index.ts`, если нужен другим.
5. Тесты рядом с кодом, правила сервиса покрыты юнит-тестами.
6. Фронтенд: `api` → `model` → `components` → экспорт в `index.ts` → использование на странице.
7. README модуля обновлён, при архитектурных изменениях запись в `DECISIONS.md`.

## 8. API-контракт и документация
- Вход каждого маршрута валидируется zod-схемой; ответы описаны DTO. Схемы, общие для клиента и сервера, лежат в `packages/shared` — типы клиента не пишутся руками.
- Контракт описан в `docs/TZ.md` (§7) и в тестах маршрутов; ошибки — `application/problem+json` с машиночитаемым `code`.
- OpenAPI (`@fastify/swagger`, `/api/docs`) **не реализован** — это Backlog, а не текущее состояние. Ручные коллекции для проверки — в отчётах сессий и `docs/ops.md`.

## 9. Как это масштабируется
- Новый функционал = новый модуль или фича, старый код не трогается.
- Вынос в отдельный процесс: `worker` уже отдельный запуск. Тяжёлый модуль (например, обработка фото) можно вынести в отдельный сервис, потому что он общается через публичный интерфейс и события.
- Рост нагрузки: сначала индексы и кэш, затем реплика на чтение для `catalog`, затем вынос `catalog` отдельно.
- Над монолитом не делаем преждевременных микросервисов: добавляем их, когда есть измеренная проблема.

## 10. Граф зависимостей

Актуальный граф строит dependency-cruiser, он же проверяет правила из §6:

```bash
cmd /c "pnpm depcheck --output-type dot > tmp/deps.dot"
# PowerShell: cmd пишет файл без BOM; Out-File добавляет BOM и dot падает.
# SVG: нужен graphviz (dot). В репозитории уже лежит собранный граф:
#   docs/architecture/deps.svg
```

`docs/architecture/deps.svg` — полный граф импортов API, web и общего пакета.
Красные рёбра означают нарушение правил (в текущем состоянии их нет) и
должны ломать CI. Сам граф не читается глазами целиком; он нужен как
доказательство, что границы модулей реальные, а не только на словах.
Карта блоков в §2 — человекочитаемая версия того же графа.
